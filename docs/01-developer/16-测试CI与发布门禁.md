## 1. 目标

自动化必须同时守住 C++ 正确性、WASM/浏览器生命周期、内容契约、本地存档、云同步和发布缓存。原生测试快不等于网页可玩；浏览器能跑一遍也不等于跨设备不会丢档。

## 2. 测试层级

| 层 | 运行频率 | 覆盖 |
| --- | --- | --- |
| 静态 | 每次提交 | clang-format/tidy、编译、include 层级、Schema、ID、文档链接 |
| Native 单元 | 每次提交 | C++ Runtime/Gameplay/ContentCore/迁移/合并 |
| Native 属性/模糊 | PR/夜间 | 解析器、Operation、任务图、效果、存档 |
| WASM 单元/集成 | 每次 PR | 编译差异、桥、内存、异常策略、内容加载 |
| 浏览器场景 | PR/夜间 | Canvas、DOM、输入、音频、IndexedDB、生命周期 |
| 核心回放 | 每次 PR 核心集 | Web Single + Native Core 离散状态一致；不等待完整 Windows 宿主 |
| Pthreads 回放 | Threads 通道建立后的受影响 PR/夜间 | Single/Pthreads 结果一致与性能收益；Deferred 时不阻塞 Single PR |
| 同步合同/服务 | IDL 建立前每次 PR 跑 mock 合同；服务建立后的受影响 PR | API、PostgreSQL 事务、幂等、冲突、迁移 |

| 部署/回滚 | 候选版 | CDN/Service Worker/API/DB 灰度与回滚 |

## 3. C++ 静态与单元门

- Clang/MSVC 至少两套编译器在支持矩阵构建纯核心。
- 警告视为错误；例外按规则编号和范围抑制。
- clang-tidy/自定义检查禁止跨层 include、裸 owning pointer、平台宏进 Gameplay。
- ASan/UBSan 原生夜间运行；适用时 MSan/TSan 独立实验。
- 单元测试注入时钟、随机、存储、网络和物理；不访问真实浏览器/数据库。
- 属性测试覆盖效果叠加、任务幂等、Operation 重放、合并交换/结合条件和迁移。
- 模糊测试内容包、快照、操作和 API payload 解析器。

## 5. 浏览器自动化

真实浏览器驱动完成：

- 冷缓存/热缓存启动、能力探测和加载进度。
- 键鼠、手柄模拟、DOM 焦点、全屏、DPR/缩放和窗口尺寸。
- `visibilitychange`, `pagehide`, blur/focus, reload, WebGL context lost/restored。
- IndexedDB 保存、事务失败、配额、旧 Schema、多标签写锁。
- Service Worker 首装、等待、激活、旧标签、新版本、离线和回滚。
- Web 单线程必跑；线程版只在正确头部环境跑并检查选择器。
- 控制台 error、unhandled rejection、CSP/COEP 违规和长任务为测试产物。

Chrome/Edge/Firefox 为主要 CI 矩阵；Safari 需要 macOS runner/人工门。不能用一个 Chromium 结果代表所有浏览器。

### 5.0 F1 真实移动的 QA 尝试预算与有界换轴

`tests/browser/web-host-lifecycle.mjs` 到达各世界交互时，必须继续通过 Playwright 键盘按键驱动真实移动；不得传送、直接改姿态、提交 Objective 或按浏览器名称放宽判定。到达容差、碰撞和 Gameplay 状态仍由现有运行时真相决定。

移动驱动不能再以一段固定墙钟作为全路线的进度真相。它在第一次权威玩家快照上计算扣除到达容差后的 X/Y 轴剩余距离，以 80 mm 保守进展量化，并按“量化格数 + 8”生成 10–256 次的有界输入尝试预算。360 mm 的短距离只获得 13 次尝试；旧 CI 从结算选择点返回 `(-10500, -600)` 的约 17,240 mm 剩余距离获得 224 次，不会因 Firefox 单次 Playwright 调用较慢而被固定 10 秒提前截断。

每轮先从扣除容差后的轴向 `remaining` 选择较大未完成轴为 `primary`，平局固定选择 X；按目标方向发送既有成对键，只允许朝目标的单轴真实移动。当前轴须连续 3 次权威玩家快照都未减少该轴 `remaining` 才标记为 stalled；另一轴仍未完成时切为 `alternate`，并同样最多 probe 3 次。任一轴取得进展就刷新全局 `best`、清空本轮两轴 exhausted 状态并按最新剩余距离重选 `primary`。只有一个未完成轴时也必须完成 3 次 probe 才失败；两个未完成轴必须在同一无进展轮内都耗尽，才以 `axis-strategies-exhausted` 失败。换轴继续消耗原 `attemptBudget`，不得增加预算、放宽 probe、反向 detour、传送或按浏览器/目标坐标/碰撞体做特判；总预算耗尽仍以 `attempt-budget-exhausted` 失败。

每次输入把 `attempt / strategy / axis / keys / beforePose / afterPose / beforeRemaining / afterRemaining / best / transition` 写入当前 movement attempt 的 `trace`；trace 受同一 256 次总上限约束。成功和失败都保留 `attemptsUsed / attemptBudget / minimumPositiveProgress` 与轴向终态。helper 失败时必须把包含 trace 的 partial `movementAttempts` 传播到顶层失败结果，并在浏览器关闭前保存 `<target>-movement-failed.png` 全页截图；不能只序列化 error string。预算、主轴选择、3 次换轴、alternate 进展回主轴、单双轴耗尽、预算上限和失败 trace 合同随脚本启动执行，也可由 `node tests/browser/web-host-lifecycle.mjs --movement-budget-self-test` 独立执行。

GitHub Actions run `29268579868` / job `86880234701` 的历史失败继续保留：Chrome、Edge 与此前全部构建门通过，Firefox 151 在第 6 Beat、任务尚未结算且 Operation 数为 0 时被旧 10 秒 QA 墙钟截断。后续 run `29400964321` 已证明距离预算不再被固定墙钟提前截断，但 Firefox 在 24/223 次尝试时停在通用 GroundBlocker 边界；artifact 的最终坐标与旧 run 落在同一空间区域。根因是旧 helper 在 X 未完成时永不尝试仍未完成的 Y，而不是 Gameplay、碰撞真相、奖励事务或训练恢复回归。本节修复只调整 QA 键盘路线调度和失败证据。最终 run `29429233737` / job `87399847869` 已对 PR merge SHA `48d3c842f418f9d9866205d7fc87b561c76095e3` 通过 MSVC/Clang Debug+Release、Web Single Debug+Release、Chrome/Edge/Firefox 和证据上传，并由 Actions/PR 元数据绑定 head `6caf38c45223b6c5024c1e205d659b448362e22f`，QA-003 因此关闭；该成功不替代既有本地 exact-head 链，也不把 G1、训练恢复、玩法时长、系统型 Demo 或 F1 整体写成 Verified。

### 5.1 F1 authored choice 路线合同

F1 全流程浏览器脚本对 Definition 已作者化 `choice_available` cue 执行以下固定顺序，禁止以 QA hook、直接完成 Objective 或 fixture flow 缩短：

1. 移动到真实交互并按 F；等待正式 DOM choice 可见，同时断言 Objective 完成数与 selection 数均未改变。
2. 核对按钮数量以及每项 DOM `interaction/selection` 顺序与权威 `projection.choice_options` 完全一致；玩家可见 label/hint 非空且不泄露 Stable ID。
3. 从第一个真实按钮焦点开始，以 Arrow 键移动到路线目标，再用 Enter 触发正式 Action intent；不得调用 `__tgdQuestUi.dispatchAction` 代替玩家输入。
4. 只有同 generation、同 projection sequence/checksum 且 wire `messageSequence` 更大的 close，或 sequence/messageSequence 均更大的非 choice replace，才能结束 choice；随后断言 Canvas 恢复焦点、Objective/selection 各只增加 1，短等待不产生第二次推进。
5. 对没有 `choice_available` cue 的后续路线、调校和结算选择做反向断言：具体世界 F 继续推进，期间不得发布 choice event 或转移到 DOM 菜单。

每次 authored choice 保存一张包含 Canvas 与 DOM 的全页截图，并把 open/authority identity、close/replace disposition、前后 Objective/selection 和焦点状态写入报告。该脚本是自动化快跑：`beatTargetsMet=0`、`playableTargetMet=false` 必须保留，Web Host 标题、英文开发 HUD、Profile 修复按钮或 lifecycle QA 控件存在时不得标为无开发界面 player mode 或 P01–P05 真人证据。

### 5.2 F1 实际任务反馈路线合同

同一两条全 7 Beat 浏览器路线还必须从真实世界/战斗输入收集当前 1.6 的非 choice raw signal，禁止调用 QA 发布、直接构造 projection、复制 UI fixture 或以 classification 选择事件。每个检查点至少保存 wire/projection identity、source、focus Objective、polarity、Definition 派生 classification、primary/secondary 的 result owner + status + reason，以及 Active/Defeated Actor 集合。

- 已提交线索的另一作者化交互必须得到 `ignored_repeat/selection_already_committed` 且 Objective/selection/checksum 不增加。
- 两路线分别覆盖 cross-belay accepted-positive 与 quick-hitch accepted-negative；后者的负向只能来自 Definition selector，不能由 App ID 分支推导。
- 未读码鸣铃为 rejected/prerequisite_incomplete，读码后同一世界交互 accepted；拒绝尝试零推进，accepted 只跟随一次 Quest command。
- take-mark/cross-flower-line 完成后的 phase 必须来自真实相邻 Objective，并在 Encounter 激活后分别看到正确训练 Actor；不能扫描 cue/rule 推断阶段。
- 檐守反制为 accepted trigger + secondary N/A；翻花重击打错目标为 accepted trigger + rejected wrong-target outcome，且发布时新证明靶已 Active、旧训练架已移出 Active snapshot。

两条路线都要继续走过后五 Beat cue-less world choice、四阶段 Boss、双结算、奖励持久化和 replay probe。它们是自动化功能证据，不替代 Edge/Firefox 远端矩阵、200%/辅助完整矩阵、无开发界面 player mode、P01–P05 或真实分钟。当前 16 条规则已补齐两个训练 frontier 的 paired recovery；它们的实际 App 路线门见 5.3，但仍不能冒充完整安全点快照或失败后离开返回。

### 5.3 F1 两训练前沿实际恢复路线合同

高水痕/迎风路线在檐守 frontier、循钟声/背风路线在翻花 frontier 各执行一次真实玩家倒地与重试。测试不得直接调用 recovery helper、写 stance、传送回战斗线或构造 UiEvent；必须按以下顺序取证：

1. 从真实敌人攻击等到玩家 `active=false`，再等待严格更新的 `recovery_offer`；断言 source、focus Objective、Definition 派生 classification、N/A 双结果槽、Active hostile 与倒地前 Quest checksum 一致，且 completed/selection 不增加。
2. 截取 offer 后显式聚焦可聚焦 Canvas，以真实 `R` 输入重试。先独立等待 retry count +1、玩家 Active/120 HP、位置等于权威安全点、同一训练 phase 只有一个 Active hostile；不能用延长 UiEvent 等待掩盖输入或组件恢复失败。
3. 只有 Session、Encounter、Combat 重试都成功，且 Quest/Objective/checksum/完成数/选择均未漂移时，才接受 wire 与 projection sequence 都严格大于 offer 的 `recovery_resume`。仅当 retry 后 stance 与倒地权威 stance 不同时，既有 `switch_stance` 才必须在后续 Combat Tick 真正产生匹配结果；stance 已匹配时不要求该事件，但两种路径都必须看到后续三组件同步 Tick 与 matching Actor snapshot。命令未生效、非法 stance、早于倒地的 retry Tick、重复 mark、三组件 Tick 不一致、Quest 或 Objective 漂移必须由 Native 正负例证明不发 resume。
4. fresh resume 后，以 `eligible + idle + failure-retry` 权威审计 Tick 至少推进 3 Tick，再按一次重复 R；继续用审计 Tick 等待观察窗口，断言 retry count、message sequence、Objective 完成数、selection 与 Beat 均不变。随后从安全点用正常移动回地面线标，等待同一 phase 的敌人真正重新产生可守/可闪避攻击，并继续完整 7 Beat、cue-less world choice、Boss、双结算、奖励与 replay probe。

pre-commit Chrome 候选报告为 `.tmp/f1-recovery-02-precommit-canopy/report.json` 与 `.tmp/f1-recovery-02-precommit-drain/report.json`：两者分别记录 offer/resume message sequence、同一 Objective、Quest checksum/完成数/选择不漂移、retry 0→1、恢复后攻击以及 0 console/page/request error；新鲜 Web Single 为 603/603。报告仍必须保留 `beatTargetsMet=0`、`playableTargetMet=false`，且由于工作树未提交，它们不能替代 exact-commit 重链和远端 Edge/Firefox 聚合。

本门只证明檐守、翻花两个精确 frontier 的 App state/evidence。三个组件之间仍无 prepare/commit/rollback，跨组件 defeated history、失败后离开返回、刷新恢复、其他 frontier、正式 recovery DOM Action（offer 首焦 retry、leave 可达、拒绝保留 last-valid）、完整辅助技术矩阵和真人时间均继续 Open；Canvas `R` 不能被写成正式恢复面板 Action 已完成。

### 5.4 Demo 0.8.2 Workbench → Web Preview 路线

`tests/browser/system-demo-workbench.mjs` 只在已存在的 `web-release-single` 真实产物上运行，启动本机 Workbench 与 Edge，并完成一条不可用纯 Node/fixture 替代的作者路线：

2. 让重复 interaction 触发唯一 C++ 共享目标诊断，通过 locator 回到精确对象，再删除旧 interaction 修复诊断并保存 revision 4。
3. 对 fresh package 执行 Launch；只有真实 Axmol Host 报告精确 token/generation ready 后，候选 iframe 才成为可见 live frame。
4. 修改并保存 revision 5；拦住新 package 请求时必须继续显示 generation 1，释放后才以 generation 2 Safe Reload，且两次 package SHA 必须不同。

6. 记录五张全页截图，并要求主页面与所有 Host frame 的 console/page/request error 均为 0。

### 5.5 Demo 0.8.4 工艺试用与返工路线

`tests/browser/system-demo-web-host.mjs` 在 Demo 0.8.3 回归路线之前，必须从同一 1.3 canonical package 和同一真实 Axmol Host 完成以下工艺路线：

1. 从作者起点以真实键盘移动到工位范围，按 `C` 进入工艺模式；距离外不能打开，Presentation 不能直接改变 Craft 状态。
2. 选择 `requires_rework` 材料，先提交后序 operation；断言 disposition 为错序且操作数、阶段和 checksum 不漂移。
3. 依次提交两项 authored operation，只有完成 `2/2` 后才可试用；按 `T` 首次雨试必须进入 `rework_required`，并精确增加一次 trial 与 mistake。
4. 按 `G` 执行 authored rework 后返回 `trial_ready`；第二次 `T` 才完成 output，最终为 trial `2`、mistake `1`、rework `1`、completed `true`。
5. 退出工艺模式后继续关门阻挡、幂等开门、自然倒地、`R`、两波/两目标/terminal 和终局 `R`；首次死亡恢复还必须证明 Craft、thin runtime 与 Encounter 同时回初态。
6. 保存工位/需求、失败返工、复试成功和既有战斗回归截图；console/page/request error 均为 0。

Native `craft_session` 另覆盖直接通过材料、错误阶段、未知目标、两种材料、restart 与双 Session checksum。该自动路线是实现者快跑，不满足非实现者试玩、真实工艺从业者审阅、Windows 可见窗口、三浏览器或 20–30 分钟人工路线。

### 5.6 Demo 0.8.5 工坊经营与路线后果

`tests/browser/system-demo-web-host.mjs` 在同一 1.4 canonical package 与真实 Axmol Host 上，把 0.8.4 工艺路线扩展为以下经营/世界后果门：

1. 初态必须显示资金 `100`、两种材料库存 `1/2`、空闲工位、未完成订单和两条关闭的 blocker；Presentation 不保存第二份经营状态。
2. 购买低成本返工材料必须原子得到资金 `100→70`、库存 `2→1`、品质 `6500` 和 occupied；错序 operation、未知材料、库存或资金拒绝均不得产生额外漂移。
3. 首次雨试失败、返工和第二次试用后，品质必须由 authored `6500 + 1900` 得到 `8400`，达到订单最低 `8000`；未完成或品质不足不能交付。
4. 交付必须一次性释放工位、增加奖励 `25`、得到资金 `95` 并通过 authored interaction → mechanism → blocker 链打开右侧捷径；重复交付不得重复资金、事件或路线。
5. 玩家必须实际穿过右侧捷径，同时左侧主门继续阻挡；之后仍按原 operate 路线开主门并回归重复触发、自然倒地、两波/两目标/terminal。
6. 死亡与终局 `R` 必须恢复资金、库存、工位、品质、订单、Craft、两条 blocker、Encounter/Combat 与作者 safe point；console/page/request error 均为 0。

Native `workshop_session` 另覆盖两条成本/品质路线、资金不足、重复 initialize、一次性结算、restart 与双 Session checksum；package 测试覆盖 1.4 sections 22–24、语义诊断和 Craft + Workshop canonical 重编码。Workbench 的 Workshops/Workshop Orders 面板仍是 update-only，真实浏览器门必须继续证明 revision/lease、Launch/Safe Reload 和无效草稿保留。该路线不满足 Windows 可见窗口、三浏览器、跨包/离开返回聚合恢复、非实现者试玩或复杂地区经济。

## 6. DOM/可访问性

- 语义/ARIA/焦点图、隐藏控件、按键提示、文本溢出和本地化。
- Canvas 关键状态有 DOM 等价摘要。

| JS authoring | `schemaVersion`、规范 JSON SHA-256、runtime projection SHA-256、`revision/savedRevision` | DEV validator、`.tgdsbx` 或可玩性 |
| validated owning package | `.tgdsbx format`、source/projection hash、fingerprint、package SHA-256、byte length、compiler 名称/版本、toolchain hash、artifact hash | Session 已建立或 Preview 正在运行 |
| running Preview/Session | package SHA-256、`generation`、state checksum、command/event sequence | 编辑器保存、编译或重载尝试已经成功 |

`platforms.windows.surface` 只接受 `visible-window-preview`，并记录 OS、compiler/toolchain/artifact、可执行文件 hash、graphics API/adapter/driver、运行 Session 与 report/screenshot/video hash。命令行 Core CTest 即使通过也不得填入该字段。`platforms.web` 只接受 `web-single-preview`，固定按 Chrome→Edge→Firefox 顺序逐项记录 browser/version、WebGL2 vendor/renderer、graphics mode/adapter/driver、同一运行 Session 与三类证据 hash；三端必须与独立的 `runningPreviewSession` 完全相等。

失败必须写 `attemptedIdentitySha256`，且 `diagnostics` 至少包含一条与失败 phase 相同、severity=`error`、稳定 uppercase code 和 message SHA-256 的诊断。失败后的根 `lastValid` 与 `outcome.previousLastValid` 按下表比较：

| 失败 phase | 必须保持不变 | 允许已前进但不能下推冒充 |
| --- | --- | --- |
| `authoring` | document、owning package、running Preview/Session | 无 |
| `compiler` | owning package、running Preview/Session | JS last-valid document |
| `decode` | owning package、running Preview/Session | JS last-valid document |
| `session` | running Preview/Session | document 与已验证 owning package；二者 source/projection 必须仍匹配 |
| `reload` | document、owning package、running Preview/Session | 无；失败重载不得覆盖任何 last-valid |

`outcome.previousLastValid` 始终逐层执行 closed-shape、字段格式与层内身份校验，但不无条件要求 document↔package↔Session 仍彼此绑定：它可能已经是前一次合法失败留下的独立三层。当前结果为 `passed` 时，根 `lastValid` 必须恢复 document↔package↔Session 全绑定；当前结果为 `session` failure 时，新 document 与新 owning package 必须绑定，但 running Preview/Session 可以继续绑定旧 package。`authoring/reload/compiler/decode` failure 只执行上表的逐层 preservation 比较，不额外假设此前保留的 package 与 Session 仍互绑。任何结果的 Windows/Web 平台 Session 仍必须精确等于当前 `lastValid.runningPreviewSession`。

本合同描述“已经各有一份 last-valid 的三层链”及其后续候选/失败关闭。首次启动尚不存在任何 document/package/Preview baseline 时发生的 preflight 失败，仍需后续独立失败报告能力；不得为满足本合同伪造空 package、空 Session、generation/checksum 或 Windows/Web Preview 身份。

## 20. 机器 Schema 验证成熟度

当前 `npm run validate:design` 会解析 Schema 文件，并以项目语义断言检查数量、ID、引用、文档层级和技术基线；它尚未执行完整 JSON Schema Draft 2020-12 关键字集合。这一限制不得在交接时表述成“所有 Schema 已被标准验证器证明”。

G1/G3 工具链必须引入锁定的 Draft 2020-12 validator，提供：

- 全部现有 Schema 的正向/负向 fixture；错误字段、缺字段、重复平台/variant、非法 ID、错误版本必须失败。
- 内容工作台、Native CLI 与 CI 的同一诊断 code/JSON Pointer。
- pack/save/operation/sync IDL 的机器合同和生成类型。
- Schema 自身 meta-schema 检查、版本迁移和兼容 fixture。

在引入完整 validator 前，手写语义守卫仍保留；二者解决的问题不同，不能用“Schema 通过”替代跨引用、图可达、预算和领域不变量。

## 21. 门禁例外
