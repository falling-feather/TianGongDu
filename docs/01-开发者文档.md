## 4. 总体架构

```text
Authoring JSON
    │
    ▼
ContentCore compiler / validator ──► canonical .tgdsbx / owning document
    │
    ├──► Workbench diagnostics / Export
    └──► Runtime coordinator
             ├──► Gameplay Session / Craft / Workshop / Economy
             ├──► Actor / Wave / Objective / Combat
             ├──► Collision
             └──► Presentation asset set

Platform input ──► Action / command ──► Gameplay truth
Gameplay snapshot/event ──► Presentation / DOM read-only output
```

依赖方向：

```text
apps/* → presentation/platform/gameplay → runtime → contracts
content/tools → content-core/contracts
presentation → runtime/contracts（只读）
platform → runtime/contracts（适配）
```

- Contracts 不知道 Axmol、DOM、IndexedDB 或具体关卡。
- Runtime 不读取编辑器 label、数组下标或资源文件名作为身份。
- Gameplay 不操作 Sprite、Scene、DOM 或数据库。
- Platform 采集物理输入并提交 Action/命令，不判定任务和奖励。
- Presentation 只消费快照/事件，不反向改写玩法。

详细依赖规则见 [`10-技术架构与依赖规则.md`](01-developer/10-技术架构与依赖规则.md)。

## 6. 数据与状态所有权

### 6.1 单一真相

- 系统 Demo 作者事实只来自 [`content/design/system-demo.sandbox.json`](../content/design/system-demo.sandbox.json)。
- `.tgdsbx` 只由唯一 C++ producer 生成；JavaScript 不编码第二份包。
- Stable Asset ID、Stable Content Key 和 `SandboxAssetKind` 必须显式匹配，禁止按文件名或槽位猜含义。
- 任务、战斗、机关、奖励和随机流属于 GameCore；DOM/CSS/动画不能推进它们。
- 材料库存、工序进度、工位占用、订单、品质、返工与地区供需同样属于 GameCore；UI 不得用按钮状态、动画完成或墙钟直接产出成品。
- IndexedDB/Profile 事务和 Gameplay 状态分层；“画面显示成功”不能替代真实事务确认。

### 6.2 last-valid 与失败保持

任何作者、编译、发布或重载流程都必须：

1. 在私有候选中完成解析、校验和依赖准备。
2. 失败时保留上一份有效 document/package/Session/asset set/画面。
3. 成功时在明确安全边界一次发布。
4. 拒绝 stale generation、revision、checksum、lease 或 command sequence。
5. 不返回 partial package，不留下半开机关或半重置关卡。

### 6.3 当前 retry 边界

standalone Sandbox retry 只恢复它自己拥有的玩家位姿、interaction、mechanism、ground blocker 和本地命令状态。Demo 0.8.3 Host 的 `R` 同时重建该薄运行链与 `SandboxEncounterSession` 的 Combat/Actor/Wave/Objective/terminal，因此玩家可见页面会回到关门、满生命、零波次/目标的局部初态；但这仍是单 Host 的局部整组重建，不是跨工艺、工坊、Profile、provider/package generation、离开返回的通用 prepare/commit/rollback。实现 `DEMO-088` 聚合恢复前，文档、API、测试和 UI 必须继续明确使用“local/standalone retry”。

## 7. 编辑器与内容生产规则

Workbench 当前可从公开 UI 新增、复制、受控删除或重建 player、actor placement、ground blocker、safe point、interaction 和 mechanism；可编辑作者 label、位姿、方向、范围、区域、受控 Stable Asset 引用与既有 typed binding，并在二维画布中点击选择、拖拽/方向键移动、吸附和缩放。player 保持恰好一个，只允许 copy-and-replace；引用删除会显示影响并按已定义所有权级联。Actor Inspector 已可编辑既有敌人的 `profileId/faction/duty/maxHealth`；现有两波与两个目标可从 update-only 面板修改 predecessor、typed trigger/completion、spawn、delay、order 与 terminal，但不能新增、复制或删除 Wave/Objective，skill/loadout 也未进入本面板。材料、工位、工序、配方、订单和工坊状态尚无公共 authoring/runtime 合同，工具不得先行发明字段或把它们塞进 label/metadata。具体状态与下一步见 [`13 §2–13`](01-developer/13-编辑器与模板生产.md#2-当前能力表)。

一条合法生产链必须是：

```text
作者草稿
→ JavaScript 结构门
→ 唯一 C++ compiler/validator
→ last-valid owning package
→ canonical Export
→ Runtime candidate
→ Windows/Web Preview
```

- 结构合法不等于语义合法。
- 保存成功不等于包有效。
- 导出成功不等于已运行。
- CTest/命令行 probe 不等于玩家 Preview。
- 一个对象需要出现三次以上时，应先建立模板、稳定合同和验证器，不能继续复制专属 C++。

## 8. 必须遵守的开发准则

1. **无关平台不分叉 Gameplay**：Windows/Web 差异只存在于 Platform/Presentation 适配。
2. **不向 F1 追加系统 Demo 特判**：F1 仅是回归基线；新能力必须由通用 Definition/Session/Actor/Objective/Wave 合同表达。
3. **不复制 validator**：JS 只做安全搬运、结构反馈和诊断展示；语义校验属于 C++ ContentCore/Gameplay。
4. **稳定 ID 不由显示名产生**：禁止用 label、ordinal、数组位置、文件名或资源名作为运行身份。
5. **确定性优先**：固定 60 Hz、可序列化随机流、明确单位和稳定排序；渲染帧率不改变规则结果。
6. **权威动作只有一条路径**：UI、按键、动画回调和测试 fixture 都不能绕过 Action/command/validation。
7. **失败不污染 last-valid**：编译、资源、Session、存储或重载失败必须可重试，且不得显示虚假成功。
8. **完成声明服从可见证据**：没有真实窗口、输入、画面、失败路线和人工验收，不得标记 Preview/playable/Verified。
9. **工艺不是表现小游戏**：工艺/经营必须走权威 Action、Definition 和 Gameplay state；不得由 DOM、动画、墙钟或一次按钮直接完成。
10. **地区不能靠资源名换皮**：地区差异来自工艺、经营、材料、空间、社会和玩法合同；禁止由地名、资源名或敌人槽位推断规则。
11. **文档职责分离**：当前实现写 01/10–19，未来任务写 02，已完成事实写 03。
12. **每提交一个可回滚意图**：标题使用 `V2.2.1 GROUP type(scope): 描述（TASK-ID）`，实现、测试和文档同步。

## 10. Git、团队与交付

- 集成分支是 `主开发`；禁止直接推送 `main`。
- 根工作区由主开发独占。并行实现必须使用 02 登记的独立 worktree。
- 脏改动归原 Owner；禁止未经授权 stash、reset、checkout、覆盖或清理。
- 当前交流组只承接用户方向和文档交接，不继续写产品代码；新主开发启动后成为唯一集成 Owner。
- 不再预先维持多条长期专业组。普通任务由一名实现者、一条分支直接认领；常态最多两条功能分支并行。
- 工作任务、分支、工作树和 Owner 只以 [`02 第 0 节`](02-版本规划与验收.md#0-项目对接控制面) 为准。
- 写入链固定为：`[ASSIGN] → [READY-FOR-VERSION] → [VERSION-TOKEN] → commit → [HANDOFF] → [QA]`。
- VERSION-TOKEN 必须写精确基线、唯一工作树、允许路径、标题和失效条件。
- 暂停/归档只停止任务，不删除分支、worktree 或历史；恢复时从同一长期任务和最新接受根继续。
- QA 只在不可变候选或版本候选出现后按需建立，不为每个微提交常驻。
- Schema、包、API 与测试是功能交付的一部分，不以“合同包体组”形式脱离当前可见版本长期推进。

## 11. 工作项 DoR 与 DoD

任务进入 `Ready` 前必须写清：

- 玩家或生产价值、范围和非目标。
- 单一 Owner、必审角色、状态 Owner 和接口边界。
- 精确权威输入、稳定 ID、数据/错误/版本变化。
- 正常、失败、重复、stale、重试、刷新/重载和性能适用项。
- 产物、测试、人工路线、风险与回退。
- 文档更新位置和提交标题。

功能只有同时满足下列条件才能标为 `Verified`：

- Web Single 与适用 Native 路径真实可达。
- 正常、失败、重复、重试和旧状态都有证据。
- 内容不是 Runtime ID 特判；第二个实例不需要新建专属代码。
- 自动化、真实浏览器/窗口、人工体验和性能证据与候选 commit 绑定。
- 文档、迁移、缓存失效和回滚已同步。
