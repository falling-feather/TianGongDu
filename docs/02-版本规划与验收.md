## 1. 总体开发规划

### 1.1 长期产品预期

《天工渡》的最终价值不是单独的战斗演示，也不是一套编辑器。它是“非遗技艺体验与工坊经营 + 地区探索与社会关系 + 动作战斗与归位”互相驱动的角色扮演游戏：

1. **技艺体验**：玩家亲手观察需求、选择材料、执行工序、判断失误、试用、维修或返工；真实工艺依据资料和从业/研究审阅区分史实与幻想改编。
2. **模拟经营**：玩家管理有限材料、工位、订单、品质、成本、关系和公共工程，不依靠挂机等待或无限倒卖。
3. **地区生活**：每个地区的工艺、生产网络、空间、社会问题、敌人/Boss 和归位后变化形成独立玩法，不是同一套系统换美术。
4. **动作归位**：战斗处理眼前危险并验证器物用途；制作、调查和经营结果改变战斗、路线与可用裁定。

三地区的长期差异以 [`07-1.0地区与内容蓝图.md`](07-1.0地区与内容蓝图.md) 为权威，当前规划只摘要其验收方向：

| 地区 | 工艺与经营 | 探索/冲突 | 不能退化成 |
| --- | --- | --- | --- |
| 江南水路 | 纸伞、染色、工坊协作、水路与公共维护 | 天气、导流、保护和公共工事 | 把伞器战斗放进蓝色水乡地图 |
| 龙泉山炉 | 选矿、锻造、工序调校、订单信誉和多工种协作 | 温度、材料、受力、矿炉高差和精确反击 | 江南流程换成剑与红色炉火 |
| 徽州墨岭 | 制墨/砚田、契约、商路、物流和资源分配 | 证据、规则、同伴调度与更多非战斗裁定 | 把契约写成纯文本对话或数值菜单 |

当前先做系统型 Demo，是为了在扩大内容生产前证明四件高风险事实：

1. 一条工艺流程既有可操作的技艺判断，也有可持续的经营取舍。
2. 战斗循环有足够操作差异，并与制作结果、地区环境发生真实联动。
3. 设计师能用工具创建、修改和验证工艺经营与战斗内容，不靠程序逐项硬写。
4. 同一内容和 Gameplay 能在 Windows/Web 可靠运行、保存和恢复。

这四个事实没有成立前，不恢复长剧情、正式资产和三地区量产；但工艺经营与地区差异本身不是“Demo 之后再做”的附属项。

### 1.2 江南工艺经营与战斗系统沙盒

玩家从一处小型江南工坊/水路场地开始：

- 看见一项具体的维修或交付需求、有限材料、工位状态和地区条件。
- 通过观察与选择进入一段可操作的伞器维护/调校；具体工序在内容写入前必须有研究来源，不凭想象冒充非遗事实。
- 管理少量库存、工位、成本、品质和交付；失误可返工或产生有用途的次品，不一键吞掉材料。
- 在场地中试用成品，使其改变一条探索路线、器物能力或战斗解法。
- 依次面对至少两组不同组合的敌人，战斗所得材料/知识或地区变化回到工坊。
- 使用移动、轻重击、防守、闪避、两种架势和每套两到三个有区别的技能。
- 能死亡、重试、离开并重新进入。
- 工艺中间品、库存/订单、关卡、机关、波次、敌人和技能状态恢复正确。
- Windows 与 Web 读取同一包并产生一致 Gameplay 结果。

设计师能在编辑器中修改位置、材料、工序、工位、订单、波次、目标和资源，保存后直接重载上述场地。当前唯一 `system-demo.sandbox.json` 仍只是工程骨架；它必须通过通用合同演进为该体验，禁止把江南/F1 ID 写进 Runtime。

## 4. 分阶段任务细化

### 4.1 D1｜首个可见 Host

- 用唯一系统 Demo 源做正例，负例只由内存 mutation 产生。

### 4.3 D3｜工艺经营沙盒

Owner：GAME；CONTENT、TOOLS、UI、QA 必审。

必须交付：

- 通用 material、workpiece、workstation、process/step、order、inventory/workshop state 与 region modifier 合同；字段有界、版本化、可迁移。
- 权威流程是“观察需求 → 选材 → 工序操作 → 试用 → 维修/返工 → 交付/留谱”，关键工序由 Action 驱动，不能由 DOM、动画或墙钟直接完成。
- 第一版只管理一处小工坊、一个活动订单和少量材料/工位，但必须存在库存、成本、品质或用途之间的真实取舍。
- 失败不吞掉全部材料；按 Definition 产生可返工中间品、次品或信息，并可安全重试。
- 制作结果至少改变一项探索路线、器物能力或战斗解法；战斗/探索结果至少回流一项材料、知识、订单或地区状态。
- `CONTENT-003` 只用通用合同制作江南伞器维护/调校代表流程。工序名称和因果必须有资料来源、史实/推断/幻想改编标记和内容审阅。
- 不按 `system_demo`、江南/F1 ID、资源名称、UI 文案或 fixture 序号分支。

### 4.4 D3｜战斗沙盒

Owner：GAME；DEV/TOOLS/ART/QA 必审。

必须交付：

- 通用 player/enemy profile、阵营、职责、loadout 和技能引用。
- 两种架势，每套至少两个有明显差异的主动技能；冷却、消耗、范围和效果由数据定义。
- 三种普通敌人职责：近战压制、远程/骚扰、侧击/包抄；另有一个精英验证位。
- 两到三组敌人组合；多个敌人可以同时施压但有明确进攻令牌和可读提示。
- wave completed → objective completed → terminal 的权威事件链。
- 至少一个制作结果通过通用器件/效果引用改变战斗或场地，不写工艺名称特判；战斗结果按通用掉落/证据合同回到工坊。
- 不按 `system_demo`、F1 ID、资产名称或 fixture 序号分支。

### 4.5 D4｜聚合状态恢复

Owner：GAME；Runtime、Platform、TOOLS、QA 必审。

聚合候选至少包含：

- package/provider identity。
- player pose/resources/stance/cooldown。
- material/workpiece/process progress/workstation/order/inventory/workshop state。
- interaction/mechanism/dynamic collision。
- Objective/Wave 状态。
- Actor/Encounter/Combat 状态。
- active safe point 和 Preview generation。

只有全部 prepare 成功才 commit；任一失败保留旧状态。死亡 retry 恢复 authored safe point 和沙盒初态，旧 generation 命令失效；离开返回和整包 reload 分别建立独立证据。

### 4.6 D5｜表现与验收

- UI：生命、体力/定力、技能/冷却、工序/材料/品质/订单、互动提示、重试和编辑器状态；键鼠/手柄/焦点清楚。
- ART：工位、材料状态、成品/次品、不同对象和敌人不靠颜色也能辨认；攻击前摇、范围、命中和危险方向可读。
- QA：Native 双工具链、Web Single、Chrome/Edge/Firefox、工艺正常/失误/返工、战斗、失败/重试/重载、截图、性能和真人试玩。
- 主开发：代码 Review、跨组冲突、最终证据 manifest 和 Demo 版本封装。

## 5. 系统型 Demo 放行条件

以下全部成立才可称“系统型 Demo 可运行”：

### 5.1 工具

- 非程序人员能创建/修改场地、对象、工艺/订单/工坊数据、两波敌人和目标。
- 保存、加载、Export、Launch、Reload 可重复。
- 重复 ID、缺资源、工艺图/任务图断路、越界和不可达路线有准确诊断。

### 5.2 工艺与经营

- 玩家必须亲手完成至少一条有观察、选材、工序、试用和返工可能的技艺流程；不能一键合成或只看进度条。
- 小规模库存、工位、订单、成本、品质/用途和交付结果至少形成两种有意义解法。
- 制作结果改变探索、战斗或地区状态；战斗/探索结果回流工坊，不能成为两套互不相干的小游戏。
- 工艺内容有来源、史实/推断/幻想改编和审阅记录；不得把未经核实的动作冒充非遗事实。

### 5.3 Gameplay

- 玩家基础动作、两架势和首批技能可用。
- 至少三类普通敌人职责、一个精英验证位和一个机制 Boss 验证位。
- 两波战斗、机关门、Objective 和 terminal 都由权威状态推进。
- 重复互动、旧命令和错误顺序不重复推进。

### 5.4 状态

- 死亡 retry 同时恢复玩家、工艺中间品、库存/订单、工位、机关、碰撞、波次、敌人和战斗。
- 离开返回、整包 reload 和失败 reload 不破坏 last-valid。
- Profile/奖励回归仍通过；重复奖励不增加 Operation。

### 5.5 平台与表现

- Windows 与 Web 读取同一 package SHA，核心 Gameplay trace 一致。
- Chrome、Edge、Firefox 通过适用路线。
- 每类工位/材料状态/成品结果、对象、敌人职责和攻击提示清楚可辨。
- 没有依赖开发控制台、QA hook 或手工改文件的关键步骤。

### 5.6 证据

- 自动化、真实窗口/浏览器、截图/日志、性能和真人试玩都绑定同一候选 commit。
- 至少一名非实现者从编辑器制作/修改一条工艺经营流程和战斗场地，并完成完整试玩。
- 至少两名目标玩家能说清自己的材料/工序/经营选择如何影响试用、战斗或交付；只完成按键序列不算技艺体验通过。
- 已知限制写入发布说明；未完成项不使用 `Verified`、`Preview-ready` 或 `playable`。

## 6. 必须保留的回归基线

系统 Demo 开发不能破坏现有：

- F1 7 Beat、两路线、四阶段 Boss 和两种结算。
- Profile/IndexedDB 奖励原子提交、Head CAS 和 `rewardDedupKey` 去重。
- Native/Web 固定回放和 checksum。
- Quest UI 的权威事件、选择意图和 stale/close 门。
- 两个训练前沿的恢复证据。

这些项目只作为回归门，不再在 02 复制逐提交实现史。精确历史和旧候选边界见 [`03`](03-发布历史.md)。

## 7. 非目标

Demo 完成前不优先：

- 新手引导、长对话、剧情演出和 60 分钟 F1 内容填充。
- 最终角色/场景美术、完整语音和正式本地化。
- Android/iOS 正式版、完整云服务、账号和商业化。
- 三地区量产、完整 NPC 关系网和正式大型 Workbench。
- 任意脚本、无界任务图、通用模组或动态 NavMesh。

三地区**量产**是非目标，但地区身份合同、江南代表体验和后续龙泉复用门不是非目标。出现上述需求时，先登记为后续计划，不得挤占 D1–D5。

## 9. Demo 之后

系统型 Demo 通过后，依次恢复：

1. 把江南首两个真实内容段做到稳定、非重复、可由工具生产，并扩展工坊、关系和公共维护。
2. 扩展对话、关系、工艺研究、地区经济和完整任务图。
3. 用龙泉的选矿/锻造最小实例证明共同框架可以承载不同工序、经营和空间，不是只适配江南或替换美术。
4. 再以徽州的契约/商路/非战斗裁定校验第三种地区语法。
5. 重新评审 M1 江南地区 Alpha 的五小时内容生产。

三地区、14 Boss、24 核心 NPC 和长期更新模型仍由 [`00-项目总纲.md`](00-项目总纲.md) 约束，不在系统 Demo 阶段提前量产。

## 10. 计划变更规则

- 新事实先更新对应 10–19 开发手册；完成提交再进入 03。
- 当前任务、Owner、依赖、估算或验收变化必须同步本文件。
- 产品支柱或长期技术路线变化必须新增 ADR。
- 阻断项必须写触发条件、Owner、回退和解除证据。
- 任何“完成”必须由 QA 对不可变候选给出明确结论；主开发负责最终集成，不以聊天口头结论替代文档。
