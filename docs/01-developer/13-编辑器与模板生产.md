# 13｜编辑器与模板生产

> 状态：Active
> 当前范围：系统型 Demo 的轻量地区、工艺经营与战斗编辑器，以及 canonical 内容生产链
> 最后更新：2026-07-26
> 维护者角色：关卡工具组；ContentCore、Gameplay、内容、美术和 QA 必审

本文件说明编辑器现在能做什么、下一版必须做什么，以及工具和 Gameplay 的所有权边界。完成过程和提交证据统一进入 [`../03-发布历史.md`](../03-发布历史.md)，本文件不再堆叠逐提交更新日志。

## 1. 产品定位

第一版不是大型商业 Workbench。它必须真正能制作当前系统型 Demo：

- 摆放玩家、敌人、障碍、互动点、机关和安全点。
- 配置材料、工艺工位、工序、订单/需求、库存初态、品质/返工结果和地区规则。
- 配置敌人波次、触发条件、关卡目标和完成条件。
- 选择 Stable Asset ID 与 Gameplay profile/duty/skill 等已发布引用。
- 检查重复 ID、缺引用、越界、工艺/任务图断路、错误资源和不可达路线。
- 保存、加载、导出并直接启动 Windows/Web 试玩。
- 修改后整包安全重载，不要求程序员手改 C++。

角色工作室、Boss 阶段图、完整任务/对话图、三地区大型工作台和大规模资产管理属于后续能力，不进入当前 Demo 的首个放行门。首版仍必须做一条可编辑的江南工艺经营代表流程，不能以“地区工作台后续再做”为由只交付战斗编辑器。

## 3. 单一生产链

```text
authoring JSON
→ JavaScript closed-shape normalizer
→ runtime projection（移除 editor-only 字段）
→ C++ compiler / package validator
→ owning canonical .tgdsbx + diagnostics
→ last-valid package
→ Runtime coordinator
→ Windows/Web Preview
```

规则：

1. JavaScript 只检查安全结构、类型和传输边界，不复制 Stable ID、引用、图、可达性或 Gameplay 语义。
2. `.tgdsbx` 只由 C++ producer 生成；工具不能再维护第二个编码器。
3. `lastValidDocument` 只表示作者形状有效，不表示 C++ 语义有效。
4. 保存成功不等于包有效，导出成功不等于 Preview 已运行。
5. Preview 必须消费同一次 fresh compiler/provider 产物，不能读取旧 fixture 或手写镜像。

## 4. 第一版对象模型

### 4.1 共同字段

所有可摆放对象至少具有：

- 稳定 ID；label/ordinal 只供作者显示，不能成为 Runtime 身份。
- `regionId`。
- GroundPose：`xMm`、`yMm`、`heightMm`、`floorLayer`。
- `facingMillidegrees`。
- 与对象类别匹配的 Stable Asset ID。

### 4.2 六类对象

| 对象 | 第一版必须编辑 | Gameplay 所有权 |
| --- | --- | --- |
| 玩家起点 | 位姿、朝向、区域、资源、initial safe point、player profile 引用 | 移动、碰撞、架势和技能由 Gameplay profile 解释 |
| 敌人/刷新点 | 位姿、朝向、区域、资源、actor profile、职责、所属波次 | 阵营、AI、攻击令牌、技能和生命属于 Gameplay/Combat |
| 地面障碍 | AABB、层、资源 | 碰撞几何来自内容；是否 solid 由权威机制/Session 状态决定 |
| 互动点 | 位姿、范围、`operate`、typed mechanism target | Action → interaction command；DOM/按键不能直接完成目标 |
| 机关 | 位姿、`one_shot_activate`、typed ground-blocker target | 首次提交原子改变机关和 blocker；重复幂等 |
| 安全点 | 位姿、朝向、retry 类型 | 聚合恢复由 Gameplay coordinator 实现，不由编辑器执行 |

当前作者格式已保存六类对象 placement、typed interaction/mechanism binding，以及敌人 Actor 的显式 profile/faction/duty/maxHealth binding。player profile、Actor loadout/skill/AI 等字段尚未发布时，工具不得自行发明或按资产名称推断。

### 4.3 待发布的工艺经营定义

下列内容是 Demo 规划需要、但尚未形成公共合同的 Definition 域；具体字段只能由 `DEMO-084` / `DEMO-085` 的同一功能 Owner 完成实现与验证后进入 authoring：

- 材料/器件与其可验证用途。
- 工艺工位、可用工具和容量。
- 工艺配方及有序/可分支的工序步骤。
- 中间品、品质/用途结果、失误、次品与返工关系。
- 订单/地区需求、成本与交付条件。
- 工坊库存、活动工位和地区供需初态。

工具只编辑 Definition 和展示共享诊断，不计算品质、不完成工序、不结算订单。首个江南伞作实例可以使用上述通用域，但不得把“纸伞”“江南”或 F1 ID 固化为字段名、枚举或 Runtime 分支。

## 5. 人物和敌人编辑流程

0.8.2 已完成 player/Actor placement 的基础对象流程；0.8.3 已补已有敌人 Actor 的最小 Gameplay binding，0.8.6/0.8.7 再补技能/精英与 NPC 模板实例化。

### 5.1 第一版交互

1. 在对象树选择新增/复制 player 或 Actor placement；player 使用“复制并替换”保持全包恰好一个。
2. 从同类受控记录建立必需结构并给出唯一稳定 ID 建议；后续版本再从 `template_standard_enemy`、`template_elite_encounter` 或 `template_core_npc` 建立内容实例。
3. 在 Inspector 编辑作者标签、位置、朝向、区域和匹配 `SandboxAssetKind` 的资源；已有敌人另显式编辑 `profileId/faction/duty/maxHealth`。
4. 在 Wave 面板编辑所属波次、`spawnOrder` 与 `delayTicks`；profile、职责和生命不得由 label、资源名或灰盒轮廓推断。
5. 复制对象必须生成新 ID；删除对象前显示全部反向引用。
6. 删除、取消或校验失败不得修改 last-valid 文档。

### 5.2 第一版限制

- 全包恰好一个玩家起点。
- 同一个 Actor placement 不能被多个波次重复引用。
- 不允许通过显示名、资产名或模板名推断阵营和职责。
- 新增第二个同类敌人不能增加专属 C++ 类或关卡 ID 分支。
- 模板提供默认结构，不绕过唯一 C++ validator。

## 6. 波次、目标、机关和工艺经营面板

第一版需要两种图形化面板：

0.8.3 先交付当前唯一 Demo 图的 **update-only** 面板，以尽快让真实两波 Host 可调；下面的 Wave/Objective 创建、复制和受控删除仍是后续第一版完成门，不能把 update-only 写成完整图编辑器。

### 6.1 波次

- 创建、复制、删除 wave。
- 选择受控 trigger。
- 管理 enemy spawn、`spawnOrder` 和 `delayTicks`。
- 显示空波次、重复 Actor、重复顺序、断开的后续波次和容量错误。
- 第一版只支持已发布的单一 typed trigger；不开放任意脚本。

### 6.2 目标

- 创建、复制、删除 objective。
- 选择至多一个 predecessor 和一个 typed completion。
- 选择 terminal/completion Objective。
- 可视化 objective ↔ wave 依赖。
- 拒绝自环、跨域环、无 root、无 terminal、断路和不能贡献到 terminal 的节点。

工具只编辑 Definition。Objective/Wave 的运行状态、完成事实和重试属于 Gameplay。

### 6.3 工艺经营

- 从受控目录选择材料、工位、配方和地区需求，不接受任意脚本。
- 可视化工序顺序、分支、输入、中间品、失败/返工和输出用途。
- 编辑库存初态、活动订单、工位容量、成本和品质/用途阈值；不得把这些值藏在显示文案里。
- 显示制作结果会影响的器物、探索、战斗或地区状态引用。
- 拒绝无输入来源、无可用工位、不可完成工序、无限材料循环、无风险套利和不可能返工的图。
- 地区身份检查至少覆盖工艺/经营、材料、空间、社会问题和归位后变化；该检查由共享内容合同与 Gameplay validator 提供，UI 不自行猜测。

## 7. 二维场地画布

0.8.2 画布只解决地面平面编辑，不追求完整 3D 编辑器：

- 已显示 region bounds、网格、对象脚点、方向、interaction range 和 blocker AABB。
- 后续工艺面板还要显示工艺工位、材料来源/存放点、订单目标和工序涉及的空间引用。
- 已支持点击选择、拖拽或方向键更新 `xMm/yMm`；高度、层、方向、范围和精确数值在 Inspector 编辑。
- 已支持缩放、100 mm 吸附和从共享诊断定位对象/字段。
- 框选、完整 Undo/Redo、工艺经营空间引用与大型无限画布不在 0.8.2；按 0.8.3–0.8.9 的实际需要增加。
- 不用像素位置保存 Runtime 真相；画布坐标必须确定映射到 GroundPose。
- 资源预览不提供碰撞、AI、职责或玩法含义。

可达性检查必须基于 Gameplay 发布的玩家 footprint、region 和 collision 规则，不能在 UI 中另写一份简化真相。

## 8. 诊断与失败关闭

每条诊断至少含：

- 稳定 code 与 severity。
- section/domain。
- record index、对象 ID/Stable key。
- 精确 field locator。
- 可选 related object。
- 面向作者的简短说明。

第一版至少检查：

- 空、非法或重复 ID；未知字段/枚举；容量溢出。
- 缺 region/asset/profile/safe point/typed target。
- asset kind、target domain 或 binding kind 错误。
- 位姿、范围、AABB、floor、facing 越界。
- 空波次、重复 Actor、错误 spawn order。
- objective/wave 环、断路、无 terminal 或不能贡献到 terminal。
- 工序缺材料/工位、图断路、不可达输出、无限无成本循环、订单无交付结果或返工无恢复路径。
- 玩家/安全点落在 blocker 内。
- 门关闭时起点到互动点可达、门后不可达；门打开后两波空间可达。

诊断失败必须保留上一份有效 document/package/Preview。不得在错误响应中泄露文件系统路径、模块路径、栈、CAS、provider identity 或 package bytes。

## 9. 保存、导出和 Preview

### 9.1 保存

- 保存使用 revision、document lease 和 CAS。
- Open/Reload/Save/Apply 的旧响应不得覆盖新文档或抢焦点。
- conflict 明确呈现，不自动丢弃本地或远端版本。

### 9.2 Export

- 只导出当前 fresh `validatedOwningPackage.packageBytes` 的 owning copy。
- Export 不重新编译、不推进 provider generation、不清 dirty、不修改 diagnostics。
- buffer、conflict、stale 或 bridge failure 均不得返回 partial `.tgdsbx`。

### 9.3 Preview/Reload

0.8.2 已实现 Web 作者闭环，0.8.3 保持同一生命周期并让候选 Host 读取 1.2 Actor/Wave/Objective 战斗包：

1. Workbench 只允许当前 revision/document lease/prepared package lease 全部 fresh 时发布 immutable package，并以 opaque token 暴露给同源 `apps/system-demo-web` Host。
2. Host 在 `preRun` 取回该 canonical bytes，C++ Runtime/Collision/Asset Resolver 全部启动成功后才向父页发送精确 token/generation ready。
3. 新候选在隐藏 iframe 中启动；旧 live iframe 在候选 ready 前保持可见，30 秒超时、编译/校验失败或无效草稿都不替换旧画面。
4. 成功 Safe Reload 开启新的 package publication generation，并从作者定义的沙盒起点建立新 Host；不在运行中热补单字段。
5. 当前实现是本机、session-bound、单 Edge 已验收的 Web Preview；0.8.3 已证明 Launch/Safe Reload 继续接受 1.2 包，且 Host 可运行两波 Combat。Windows 可见 Host、三浏览器完整 manifest、通用跨平台聚合事务与跨版本战斗状态迁移仍未完成。

## 10. 资产边界

当前系统 Demo 登记 12 个 Stable Asset ID，并有每槽 Standard/Low 灰盒产物。Inspector 已按对象类别从受控资源目录选择匹配 kind 的 ID；敌人 Gameplay binding 与资源选择分栏显示，资源名不回填职责。后续资源面板还应显示：

- `SandboxAssetKind`。
- Blockout/Integrated/Preview-ready/License 状态。
- 缺失、wrong kind、wrong key 和低档回落诊断。
- 简单缩略图与脚点/朝向说明。

资源文件名、轮廓或 `pressure/flanker/elite` 文本不拥有敌人职责、AI、技能或碰撞。当前资产仍为 `Blockout / not-integrated / previewReady=false`。

## 12. 第一版完成定义

轻量编辑器只有在下列闭环同一候选上成立时，才能标为可用：

1. 从空白/模板建立一块非空场地，新增玩家、四个敌人、障碍、互动点、机关和安全点。
2. 配置一条材料→工位→工序→中间品/返工→交付的工艺经营流程，以及库存/订单初态。
3. 配置两波敌人、两个目标、terminal 和资源引用，并让至少一个工艺结果影响探索或战斗。
4. Inspector 与二维画布往返后数值不漂移。
5. 正常保存/加载/导出；重复 ID、工艺/任务断路、缺资源和不可达路线有准确诊断。
6. 一键启动 Windows/Web Preview，修改后安全重载。
7. 失败 compile、缺资源、失败 reload 保留上一份有效包与画面。
8. Windows/Web 消费同一 package SHA 和 Gameplay trace。
9. 至少一名非实现者完成“创建工艺与战斗内容→修错→试玩→修改→重载”人工流程。

Node 单测、C++ compiler probe、`.tgdsbx` 下载或现有对象表单都不能单独满足这一定义。

0.8.2 关闭上述第 4 项的基础画布往返、第 5 项中的六类对象保存/诊断，以及第 6–7 项的 Web 单端 Launch/Safe Reload 子集；0.8.3 又关闭第 3 项“既有两波/两目标/terminal 可修改并运行”的子集。Wave/Objective 从空创建/删除、工艺经营、Windows 同包和非实现者流程仍由后续版本完成，不能把阶段闭环写成整份第一版定义已完成。

## 13. Demo 0.8.x 编辑器落地顺序

编辑器不等全部字段和商业级体验完成后一次发布，而是跟随可见 Demo 逐版增长：

| 产品版本 | 编辑器交付 | 不提前做 |
| --- | --- | --- |
| `0.8.2`（已完成） | 六类基础对象新增/复制/受控删除或重建、二维摆放、受控资源选择、Web Launch/Safe Reload | 大型无限画布、框选、完整 Undo 历史、多人协作 |
| `0.8.3`（已完成 update-only 子集） | 敌人 Actor 显式 Gameplay binding、现有两波 Wave/Spawn 与 Objective/terminal 更新面板 | Wave/Objective CRUD、任意脚本、复杂复合任务图 |
| `0.8.4` | 材料、工位、工序、试用/返工的最小面板 | 全地区配方库、长生产链 |
| `0.8.5` | 库存、订单、品质/成本和交付面板 | 离线挂机、复杂市场模拟 |
| `0.8.7` | 从 `template_core_npc` 创建沈砚、骆青禾、阿棠的 Greybox 实例 | 24 名核心 NPC 批量生产 |
| `0.8.8` | 聚合整包状态重建、Windows 可见 Launch，并与现有 Web Preview 做同包一致性和失败保留 | 运行中跨版本热补字段 |
| `0.8.9` | 设计师流程、焦点、200%、性能和错误文案优化 | 商业级大型 Workbench |

人物和敌人不是同一种模板：

- NPC 使用 [`template_core_npc`](../../content/templates/template-registry.json)，身份/关系/日程来自 05–07；美术与导入遵循 14。
- 普通敌人使用 `template_standard_enemy`，精英使用 `template_elite_encounter`；职责、AI、技能和伤害仍由 Gameplay 数据持有。
- 编辑器可以帮助选择模板和受控资源，但不能根据名称、标签或资产文件推断 NPC 功能、敌人职责或战斗数值。

每个版本的具体 Owner、分支、资料章节和验收只维护在 [`02 第 4–5 节`](../02-版本规划与验收.md#4-小版本任务卡)。
