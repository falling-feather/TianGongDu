## 1. 一页认识《天工渡》

《天工渡》是一款浏览器首发、可向 Windows 等原生平台扩展的 2.5D 斜向全景动作与工艺经营角色扮演游戏。玩家扮演年轻的“执灯渡人”，携带一页残缺的《天工录》巡行“九州百工”，在有人生活、生产、交易、争论与传承的东方工艺社会中，通过行走、调查、交往、技艺实践、工坊经营、探索与战斗，看见器物和社会失序的真正原因，并让器物、工序、责任与关系重新“归位”。

一句话体验承诺保持为：

> 在温润繁盛的东方工艺世界里，以兵击破势、以工灯见因、以选择让百工重新归位。

项目最重要的产品边界是三条主线同等重要：玩家要亲手体验经过研究与审阅的非遗技艺；经营工坊、订单和地区生产网络；在探索与战斗中处理失序并把结果带回社会。战斗不是压倒一切的唯一核心，工艺也不是图鉴、一键合成或等待计时，经营不是脱离人物和地区的数字表。三者必须形成因果：调查带来需求与证据，工艺选择改变器物、路线和战斗，经营决定材料、订单、关系与公共工程，探索和战斗又带回新材料、知识、责任与地区变化。

当前产品处于 `Development Freeze / 设计定型前暂停`，稳定实现停在 `Demo 0.8.5 Internal Blockout`。本文件所汇总的 1.0 三地区、21 章、24 名核心 NPC 与 14 个 Boss 是完整且互相校验过的**现有范围草案**，不是已经量产完成的内容，也不是在 `PM-023/PM-024` 前不可修改的最终承诺。

## 2. 产品定位、玩家感受与明确非目标

目标体验不是“古风皮肤的刷怪游戏”，而是让玩家感到自己进入了一个温润、繁盛、可信且正在运转的工艺世界。玩家在雨棚、桥汊、作坊、矿谷、炉场、砚田、书院和商路中首先看见人的日常与器物用途，随后才看见被放大的失序。每次完整事件都应从现实需要出发，经过材料与工序判断、社会责任冲突和动作压力，最后回到可观察的日常改变；玩家记住的不应只是击败了谁，还应记得谁在维护、谁没有被署名、某项工艺为何必须这样做，以及自己的记录让谁承担了什么后果。

画面与空间的第一体验指导是《斗战神》所代表的斜向全景构图、纵深空间组织、角色与场景尺度、东方材质重量、群战层次和受控镜头调度；《暖雪》只作为俯斜视角下战斗可读性、敌我轮廓和输入简洁度的第二参考。参考只到高层设计语言，不能复刻任何可识别角色、地图、UI、剧情、动作或音画资产。《天工渡》自己的世界圣经、工艺逻辑、人物和视觉语言始终是内容真相。

正式游玩空间是受控俯斜镜头下的地面纵深空间：角色在地面 `x/y` 平面进行八方向移动，高度与楼层单独表达；地图由可读 Cell、短连接、回环和地区枢纽组成，不是纯侧视横版，也不是自由旋转的第三人称大世界。长期产品不追求无缝巨型开放世界、MMO/PvP/实时多人、随机生成替代手工因果内容、任意代码模组、以 JavaScript 复制 Gameplay 真相，亦不承诺 Web、Windows、Android、iOS 同日首发。剧情、新手引导、长对话、三地区量产、最终美术、移动端与云服务在当前暂停期都不是开发优先级。

## 3. 世界观：九州百工、三层世界与“归位”

“九州百工”不是历史中国复刻，也不是齿轮蒸汽奇观。它是以成熟手工业、贸易、公共工程、师承、行会、档案和地方社会为物质基础的架空东方世界。时代能力大致包含纸与印刷、指南、成熟水利、风力/水力/火力/人力/畜力传动、矿冶、远距离商路与档案网络；不出现电网、内燃机、工业流水线、现代枪械、无线通信和即时物流。火药可以用于矿务、信号和节庆，但不是普遍枪械体系。

世界同时以三层运转。**市井层**是饮食、居住、交易、师徒、家庭、传闻、节令和公共生活；**工事层**是材料从何而来、谁加工、如何运输、谁验收、谁维护、事故成本由谁承担；**祟局层**则是长期错误工序、用途冲突和缺失记录形成的异常回声。合格的主线必须完成“社会事件 → 物质原因 → 战斗/祟局破势 → 社会生活中的修复”，不能只在祟局里打完怪便结束。

世界只有三组常用幻想语法：工灯、工印与祟。**工灯**让玩家照见工痕、材料状态、被省略的步骤和相互冲突的证据；它不是万能扫描器。**工印**是“谁、为何、怎样、为谁制作、由谁维护”的可验证记录，也可在既有材料与能量范围内约束、引导或重排工序；它不能凭空创造物质或能量。**祟**不是单一负面情绪变成怪物，而是“重复工艺过程 + 长期用途冲突 + 记录缺失或互相矛盾”共同形成的放大回声。祟会重复或夸张错误流程，击败它只能暂时压制，真正解决仍要处理用途、维护责任、劳动署名和记录方式。

“用”在本世界至少有四层：器物的物理用途、它在社会关系中的用途、技艺如何传承、以及谁承担维护责任。“归位”因此不是修好一个物件或消灭一个敌人，而是把设施、责任、劳动与记录重新接上，并承认某些争议不能被一份整齐结论抹平。

### 3.1 天工院、天工渡与《天工录》

天工院是跨地区的公共技术与记录组织，承担渡务、录事、衡工和济作等职能。它在社会中受尊重，但会受程序、资源和记录偏见限制；它既不是万能政府，也不是隐藏邪恶组织。天工渡既指连接地区、材料、知识和责任的实际网络，也指“让技艺与责任能够渡到下一人”的公共理想。

玩家是天工院体系中的年轻“执灯渡人”，合法性来自护牒，调查依靠工灯，结论进入《天工录》。玩家不是被选中的救世主，而是在每个地区逐渐学会观察、询问、试验、承担和记录的人。《天工录》是一份会被修订、可附异议、可能犯错的活档案，不是神谕或 AI；它承担见证、索引和追问功能。玩家可选择把某一判断写为主结论、批注、异议或留白，记录本身也成为世界中的权力与责任。

“无款工印”不是邪教标志，而是没有署名或责任栏被留空的记录。它在三地呈现不同问题：江南是公共维护人人参与却无人正式负责；龙泉是名门声誉遮住了材料来源和无名劳动；徽州则是空白条款既可能被强者利用，也可能成为让普通劳动者共同署名的入口。

### 3.2 玩家身份、正史与可定制边界

玩家的固定成长弧线是“先看见被忽略的劳动，再质疑唯一标准，最后学会保留异议”。姓名、外观、肤色、发型、体型轮廓、代词、籍贯风味和处事态度可以定制，但不会以可定制背景暗藏旧日血缘、恋情或救世身份。角色可以发展关系与立场，不能靠送礼无限刷满所有人；高阶关系来自共同经历、价值判断和承担后果。

正史按层级管理：`L0` 是 00 与 05 的项目/世界硬约束；`L1` 是 07 及正式发布内容中的公共事实；`L2` 是地区材料；`L3` 是角色立场和有限视角；`L4` 是未确认概念。现实工艺内容必须把可核实史实、团队推断和幻想改写分开，记录来源、审阅者、许可与适用范围。江南伞作目前已有 `RS-CRAFT-001–002` 两项来源登记，但真实从业者审阅仍未完成。

## 4. 核心玩法：行、问、试、归

长期循环用四个动词概括。**行**是进入地区、观察时间与空间、走位、穿行和发现；**问**是与人物、器物、档案和环境交互，建立可复核的证据；**试**是亲手操作工艺、经营取舍、战斗与环境实验，让假设接受后果；**归**是把设施、责任、署名、关系和地区状态重新安排，并把结果写入《天工录》。四步不是固定菜单，而应在一个场景中自然交错。

节奏目标按多个尺度叠加：约 30 秒形成一次动作判断，约 5 分钟完成一个兴趣点或小问题，约 30–70 分钟完成一个普通子地区首轮，地区终局可拆成若干 20–35 分钟安全段，单地区约 5–10 小时。当前江南系统 Demo 的 20–30 分钟目标只是验证三条主线能否在一块小场景内互相驱动，不等于正式游戏只做短局。

探索采用 Cell、短连接、回环与枢纽。兴趣点并非全部贴地图图标：草案要求至少 35% 通过声音、地标、人物指引、工痕或玩家推理发现，至少 25% 在地区归位后产生新状态或第二用途。玩家离开再返回时，应看到工坊、市场、交通、人物日程、公共工程和敌对生态的改变，而不是只有一次性宝箱消失。

## 5. 战斗与归位

战斗资源设计区分生命、体力、定力、工灯势与证据槽；生命、定力、失序和证据不是同一个数值的不同名称。战斗的完整终点不是把生命清零，而是“破势后获得处理窗口，并用证据与工艺完成归位判断”。普通遭遇可以以护送、保护、拆解、驱散或使其降级为非敌对状态收束，Boss 则必须有直接制伏/证据不足和完整归位之间的后果差异。

**护牒兵击**承担实时动作、位置博弈、攻防读招和武器表达，设计循环是“识招 → 守身 → 夺位 → 破势 → 择终”。**工灯定印**把调查和工艺判断嵌入战斗，循环是“照见 → 引序 → 定印”，让玩家找出错误工序、布置或触发环境协作，并在归位窗口决定如何修复。两套系统共享工灯势和现场条件，但不能把工灯退化为伤害加成按钮。

第一武器线是伞器，战斗身份为中距离控场、精确格挡、借风位移和同伴掩护，三种架势为“檐守、翻花、风渡”，工艺域是伞骨、纸面、桐油和铰轴，终极掌握概念为“四时合伞”。第二武器线是剑器，身份为近身精确压制、架势切换、蓄锋反击和淬火调校，三种架势为“试锋、藏锋、回炉”，工艺域是选矿、叠锻、淬火和研磨，终极掌握概念为“百炼归一”。这两条武器线属于现有 1.0 草案；稳定 0.8.5 只实现了最小轻/重击，两架势与完整技能手感尚未放行。

敌人设计以职责和工序语义为核心，不从资源文件名推断 Gameplay。普通敌人使用 `template_standard_enemy`，精英遭遇使用 `template_elite_encounter`，武器/技能用 `template_weapon_family`；Gameplay 身份来自 [`../content/design/v1-content-catalog.json`](../content/design/v1-content-catalog.json)，美术绑定遵守 [`01-developer/14-资产管线与性能预算.md`](01-developer/14-资产管线与性能预算.md)。

## 6. 工艺、工坊经营、成长与失败

工艺循环不是“集齐材料后一键完成”，而是“需求 → 材料 → 工序取舍 → 试用 → 修理/返工 → 传承”。材料应有来源、含水、韧性、尺寸、批次或使用历史等可观察差异；操作要让玩家理解为什么这样做；失败应产生学习、可利用副产物或可恢复返工，而不是把全部投入清零。真实工艺事实与玩法改写必须在资料登记中分栏，任何幻想分支都不能冒充历史事实。

工坊与地区经营的目标是让材料、工位、订单、品质、关系、路线和公共工程形成取舍。玩家可能选择昂贵但稳定的材料，也可能用低成本材料承担额外返工；订单交付应改变人物信任、市场供给、通行路线或公共设施，而不只是奖励货币。长期经营还需讨论多工位协作、季节/天气、师徒劳动、地区供需和价格反馈，但这些都属于 `PM-023` 待定型内容，当前稳定原型只证明单工位、单订单、双材料路线可成立。

成长分为渡人能力、武器掌握、百工见闻与人物关系四条，强调横向组合而非无限等级碾压。伞器、剑器、工灯证据、地区工艺和伙伴能力应在跨区时组合出新解法，而不是让后一地区简单淘汰前一地区。失败与重试要保留已经发现的基础线索和无争议记录，回滚尚未提交的战斗与选择；长演出或长路线后要有安全点。辅助模式可以调整动作、证据、操作和时间压力，但不能删剧情、删奖励或把工艺替玩家自动跳过。

## 7. 地区架构与 1.0 范围草案

机器目录当前登记三地区、18 个大型子地区、21 章主线、18 条成链支线、25 个敌人家族、14 个 Boss、24 名核心 NPC 和 120 个兴趣点。主线预算 945 分钟（约 15.75 小时），主线加支线 1395 分钟（约 23.25 小时），完成型体验约 1800 分钟（30 小时）。这些数量经过目录和文档互相校验，但状态是**现有范围草案**；恢复制作前仍要由 `PM-023/PM-024/PM-025` 决定是否保留。

三地区不是换皮顺序。江南让玩家先看见公共维护与无名责任，龙泉把问题推进到用途、锋利、师承和危险劳动，徽州进一步讨论契约、档案和“谁的证词能够成为证据”。跨区主线由无款工印和《天工录》的记录权串联，能力也从保护/导流，发展到权衡/调校，再发展到记录/组织。

### 7.1 江南水路

江南是低平水网和密集熟人社会，雨、伞、染色、旧桥与潮闸把个人手艺和公共维护连接起来。玩家从纸伞小故障进入，逐步学习移动、交互、檐守、精确格挡、照见、引序、定印和关系协作，最终面对外圩倒灌与“责任被切成太多小块”的地区问题。

| 子地区 | 空间/玩法语法 | 核心内容与归位后变化 |
| --- | --- | --- |
| 雨渡镇口 | 檐下路径、雨势、熟人引荐 | 教学、茶摊口述、驿使邮件；归位后出现新旅人、跨区邮件与节令摊 |
| 纸伞作坊街 | 伞骨张力、纸面含水、工位协作 | 伞器编辑、四家工坊、四时伞祟；归位后有定制部件、学徒课程和屋顶捷径 |
| 听雨市 | 叫卖声、价格波动、摊主声誉 | 跑行、报时铎与交易选择；摊位组合和行情随归位变化 |
| 染河庭 | 水流分色、媒染、污染溯源 | 三染坊立场、颜色谜题和照影战；水质影响材料与服饰颜色 |

## 10. 任务、叙事、奖励与结局

主线采用三地递进而非“收集三件神器”。江南首先让玩家看见公共维护里被遗漏的劳动；龙泉让玩家挑战“锋利和名门天然正确”的标准；徽州让玩家正面处理档案、契约与记录权。每章的冲突都应至少包含社会事件、物质证据、一个可玩的试验或动作压力、一次责任安排和可回访结果。长对话不能代替关卡状态、人物日程和空间变化。

任务由目标图、进入/退出、持久化、反馈和世界后果组成。选择应改变行动、路线、关系、资源或归位方式，不能只换一句台词。唯一奖励通过稳定 claim ID 和幂等 Operation 处理，失败或重试不能重复发奖。江南奖励偏“保护和导流”，龙泉偏“权衡和调校”，徽州偏“记录和组织”；跨区组合提供新解法，但不强迫玩家回到每个旧角落清图。

地区结局由“设施归位 + 责任安排 + 署名方式 + 异议保留”四项组合。1.0 尾声计划形成 6–9 个主要变体和不同角色来信，不追求指数级排列。最差结果可以更保守、更昂贵或关系疏远，却不以突然毁灭地区否定几十小时投入；最完整结果也不宣称矛盾永久消失。整体基调保持平和、有人继续生活、维护和争论，并为后续内容留出空间。

## 11. UI、视觉、音频与可访问性

视觉目标是温润而有物质重量的东方工艺世界。地形、建筑、器物和人物首先服务空间、用途和生产关系，再服务装饰。正式资源需要通过 Stable Asset ID、元数据、预算与许可进入内容，不可根据文件名猜玩法；当前 12 个资源槽和 24 张 PNG 是稳定灰盒资产，只证明辨识、绑定和构建，不代表角色、场景、动画或 VFX 风格已经确定。

界面原则是“世界优先、信息按需、工艺可读而非表格化”。Canvas 负责世界、角色、命中、机关与空间反馈；DOM 负责 HUD、菜单、文本密集内容、输入提示和辅助功能，但 DOM 不能持有第二份 Gameplay 状态。常驻 HUD 只显示当前行动所需的生命、体力、定力、工灯势、证据/目标和情境提示；地图、天工录、工坊与证据板属于深层面板，打开时应明确暂停或输入所有权。

键鼠、手柄和触控要映射到同一 Action Registry；键位提示必须随设备变化。颜色信息要有形状、文字、纹理或节奏冗余；声纹、报时和听觉谜题必须有视觉/触觉等价信息；字幕、字号、对比度、动态减弱、镜头震动、闪烁、输入保持/连按替代、时间窗口和动作辅助均需可调。辅助选项不应减少剧情和奖励，也不能把工艺系统悄悄替换为跳过按钮。

音频应把地区劳动声、天气、水流、炉火、木石、市场和人物日程作为空间信息，而不是只铺背景音乐。战斗读招、工艺操作和工灯证据需要稳定事件语义；正式音乐、配音和声音资产尚未制作，当前只保留事件和无障碍边界。

## 12. 简要技术落点

当前已接受但待 `ARCH-001` 复核的技术基线是 C++20 GameCore、Axmol `2.11.4 / 2.11.x LTS` 宿主、Emscripten `3.1.73`、WebAssembly/WebGL2、CMake Presets 与 Ninja，浏览器桌面端优先。模拟固定为 60 Hz，Gameplay/Runtime 状态与渲染分离；地面坐标使用量化的 `x/y` 毫米域，高度和楼层独立。代码所有权大体为 Contracts → Runtime → Gameplay，Presentation 和 Platform Adapter 只投影与适配，不在 Axmol、DOM 或 JavaScript 中复制战斗、任务、经营、奖励和存档真相。

内容长期以 JSON + JSON Schema 2020-12 进入同一 C++ ContentCore，再烘焙为带哈希的 `.tgdpack`。当前系统 Demo 使用仅供开发的 `.tgdsbx` format `1.4`，24 个 append-only sections、4 MiB 上限；唯一作者源是 [`../content/design/system-demo.sandbox.json`](../content/design/system-demo.sandbox.json)，Workbench、compiler/provider、WASM Gameplay 与 Web Host 共用这条链。模板注册表当前有 10 个模板，其中 NPC、普通敌人、精英、Boss、任务、对话、武器、子地区与工艺分别有稳定模板入口；模板只规定生产合同，不表示对应内容都已制作。

Web 采用 Canvas 游戏画面加语义 DOM HUD/菜单。存档长期方向是 IndexedDB 本地优先、Guest 可玩，云同步如启用则采用 revisioned snapshot + idempotent operation journal，并对叙事冲突要求玩家显式选择；服务候选为 C++20/Drogon/PostgreSQL/OIDC。这些云端组件仍是设计边界，不是当前已部署功能。Web Single 是 1.0 必需基线，Pthreads、Windows、Android、iOS 都必须各自通过输入、性能、生命周期、存档、部署和回滚门，不能因共享核心便宣称已支持。

当前工具侧的 Content Workbench 能编辑六类场地对象，并 update-only 修改既有 Actor binding、Wave/Objective、Craft/Workshop/Order，支持校验、Save、Launch 和 Safe Reload。它是内部生产工具原型，不是通用商业编辑器；完整 Wave/Objective/Craft 图 CRUD、完整 Undo/Redo、NPC 模板工作流、资源缩略图和跨包迁移尚未完成。

## 13. 当前设计与实现的交界

稳定 `Demo 0.8.5` 已经在一个灰盒江南小场景中证明：玩家可以移动、购买两种有限材料、占用工位、完成伞篷对齐与贴补、经历雨试失败和返工复试、比较高成本直达与低成本返工两条路线、交付订单并打开屋顶捷径，再操作主门、完成两波四敌人战斗和 terminal，并在死亡或终局后局部重试。这证明“工艺 → 经营 → 路线 → 战斗”能在一个 Host 中形成技术因果，但其工艺深度、战斗手感、场景节奏、角色生活、正式表现和 20–30 分钟真人体验都尚未定型。

旧 F1 纵切还证明过固定 60 Hz 回放、7 Beat、雨渡准备、沈砚训练、双路线、返程增援、四阶段四时伞祟、双结算、奖励持久化和 IndexedDB Guest 存档。它现在只作为历史回归线，不是当前产品目标，也没有证明真人 60 分钟游玩。设计讨论可以借鉴其中已验证的状态边界，但不能因已有代码而倒推产品必须保留所有旧结构。

## 14. 下一轮必须定型的问题

`PM-023` 需要决定目标玩家、每 20–30 分钟与每 5–10 小时的体验结构、行/问/试/归怎样真正循环、三条主线的时间与因果占比、失败/成长、战斗和工艺的操作深度，以及江南小闭环是否仍是最佳验证单元。`PM-024` 需要决定世界历史层级、天工院与地方社会的关系、工灯/工印/祟的限制、无款工印和三地区的政治经济联系、现实工艺与幻想改写边界，以及当前三地区/24 NPC/14 Boss 是否仍是 1.0 的正确规模。

`ARCH-001` 需要把现有 C++/Axmol/Emscripten、Canvas/DOM、同包双端、Workbench、存档与服务设计同最终产品规模重新比较，给出保留、调整和替换方案、迁移成本与 No-Go 条件。三项确认后，`PM-025` 才会重排 Demo 版本、工期、Owner、验收和退出条件；在此之前，`DEMO-086–089` 不自动恢复。
