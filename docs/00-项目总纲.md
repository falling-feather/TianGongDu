> 状态：Development Freeze（2026-08-26 完成收束；产品支柱继续有效，具体设计等待重新定型）

## 1. 项目定义

《天工渡》是一款浏览器首发、可向原生多端扩展的 2.5D 斜向全景动作与工艺经营角色扮演游戏。正式游玩采用受控俯斜镜头和可纵深走位的地面空间，不是纯侧视横版、自由旋转第三人称，也不是用少量事件包装的轻量页游或短篇技术 Demo。

玩家扮演年轻的“执灯渡人”，携一页残缺《天工录》巡行“九州百工”。每个地区都是有人生活、生产、交易、争论和传承的社会，不是只为刷怪而存在的关卡。玩家通过调查、交往、工艺、探索与战斗看见失序的根因，最后让器物、工序、责任与关系重新“归位”。

产品不以战斗作为压倒其他系统的唯一核心。**亲手体验技艺、经营工坊与地区生产、探索和战斗归位**必须互相提供原因和结果：工艺选择改变器物、路线和战斗；经营决定材料、订单、关系与公共工程；探索和战斗又带回需求、材料、知识与地区变化。

一句话体验承诺：

> 在温润繁盛的东方工艺世界里，以兵击破势、以工灯见因、以选择让百工重新归位。

## 1.0 体验指导优先级

《斗战神》是整体体验的第一指导：所有团队先用它校准斜向全景构图、纵深空间组织、角色与场景尺度、东方材质重量、群战层次和受控镜头调度。《暖雪》是第二参考，只用于校准俯斜视角下的战斗可读性、敌我轮廓和输入简洁度。《天工渡》的世界圣经、工艺玩法、角色与自身视觉语言始终是内容真相；参考只到高层设计语言为止，禁止复刻或近似重制任何角色、场景、地图、UI、剧情、动作、音画资产与可识别表达。

若下级文档、原型或占位资产仍写“横版”“侧视”“无纵深走位”，一律视为旧约束并回到本节与 ADR-0009 修正。F1 几何启动画面只证明宿主和生命周期，不构成视角、美术或最终渲染方案验收。

### 1.3 当前系统型 Demo 里程碑

`F1-SYSTEM-DEMO-01` 是当前生产验证里程碑，不是《天工渡》的最终产品缩减版。它把验证顺序改为：先证明工艺经营与战斗能够互相驱动，并证明团队能通过轻量工具反复制作、修改、校验和试玩这两类内容；现有 7 Beat、两路线、Boss、双结算、存档与回放继续作为回归基线。

该 Demo 必须从编辑器制作一块江南代表性的工艺经营与战斗场地，能配置玩家、敌人、障碍、互动点、机关、安全点、工艺工位、材料/工序、订单/需求、波次、触发和目标，保存/导出后直接进入 Windows 与 Web 试玩。玩家必须亲手完成一段有选材、工序、试用和返工可能的伞器维护/调校，并管理小规模库存、工位、品质与交付；制作结果要改变探索或战斗，而不是成为脱离世界的一次性小游戏。战斗至少验证两种架势、首批数据化技能、多敌人职责、死亡重试和状态恢复。灰盒可以保留，但玩家、工位、材料状态、不同敌人、机关、障碍和技能提示必须清楚可辨。

当前不优先扩写剧情、新手引导、长对话、最终美术、移动端、云服务、三地区量产或大型商业 Workbench；但“工艺经营是真玩法”和“地区不是换皮”不能作为非目标删掉。暂停状态、Owner 与 worktree 租约维护在 [`02 第 0 节`](02-版本规划与验收.md#0-项目对接控制面)，未完成任务与恢复验收维护在 02 §4、§6–7；本节只固定产品层面的验证方向。

项目最初于 2026-07-26 应用户要求暂停，并在 2026-08-26 完成第二次收束，正式进入“设计定型前暂停”。稳定集成基线停在 `Demo 0.8.5`；`DEMO-086 / Demo 0.8.6` 仅在隔离分支保存了未集成检查点，不构成产品版本完成。恢复时先读 [`02 §0.1、§4.2`](02-版本规划与验收.md#01-当前状态) 和 [`Demo 0.8.6 暂停与恢复交接`](handovers/2026-07-26-demo-086-pause/README.md)，再完成游戏设计、世界架构与技术栈三项定型；不得从聊天记录推断当前实现，也不得默认沿旧版本顺序继续开发。

### 1.4 长期世界与当前 Demo 的关系

长期目标仍是“东方工艺世界中的动作、探索、关系与归位”：玩家在真实运转的市井、水路和工事中，用伞器兵击处理眼前威胁，用工灯调查失序原因，再通过选择恢复器物、工序和人与人的责任关系。地区、角色、剧情与工艺都要服务这一体验，而不是只给战斗换皮。

当前系统型 Demo 不是删去上述背景，也不是先做一段长剧情。它暂时把首轮游玩目标收窄到 20–30 分钟，抽取长期产品最难伪装的共同底座，先回答六个问题：

1. 观察需求、选材、工序操作、试用与返工是否形成可理解、可掌握的技艺体验。
2. 材料、工位、订单、品质、关系和地区供需是否形成有取舍的轻度经营，而不是等待计时或表格加数值。
3. 移动、轻重击、防守、闪避、两种架势与技能组合是否真的好玩。
4. 工艺成品是否会改变探索、器物能力或战斗解法，战斗与探索结果是否会回到工坊和地区状态。
5. 非程序人员是否能用轻量工具制作工艺经营、场地、敌群、波次和目标，并快速进入试玩。
6. Windows 与 Web 是否能消费同一份内容、产生一致状态，并在死亡、重试与重载后可靠恢复。

当前只用江南纸伞/水路的代表性小循环验证这套底座，不同时量产三地区。后续地区必须沿各自的生产与社会结构扩展，而不是替换美术和敌人名称：

| 地区 | 技艺与经营重心 | 探索/战斗重心 | 必须形成的地区差异 |
| --- | --- | --- | --- |
| 江南水路 | 纸伞、染色、工坊协作、水路与公共维护 | 保护、导流、天气、工事协作 | 材料含水、伞器调校、市场/水路和公共维修互相影响 |
| 龙泉山炉 | 选矿、锻造、工序调校、订单信誉与危险劳动 | 材料、温度、受力、垂直矿炉和精确反击 | 用途与锋利的取舍，移动工位和多工种联合生产 |
| 徽州墨岭 | 制墨/砚田、契约、商路、物流和资源分配 | 证据、规则、同伴调度、低战斗裁定 | 记录权、林水资源和商队组织改变场地与社会结果 |

只有上述六项形成一个可反复修改、可见、可玩的闭环，才扩大剧情、长流程、正式资产和三地区生产。系统型 Demo 的详细阶段、工期估算和放行条件以 [`02`](02-版本规划与验收.md) 为准。

## 2. 不可动摇的五根支柱

### 2.1 工艺必须成为玩法

工艺不能只存在于图鉴、背景文字、一次性按键或数值加成里。玩家必须能理解并操作需求、选材、工序、工具、失误、试用、维修/返工和用途；经营层必须让材料、工位、订单、品质、关系、供需与公共工程产生取舍。它们必须改变探索路径、战斗规则、角色关系、地区生产或结局裁定。

### 2.2 战斗终点是归位

敌人可以被打倒，但完整胜利必须经历“破势—验因—归位”。Boss 的最后阶段要回答：何物失序、谁承担后果、怎样恢复用途、记录如何留下。

### 2.3 社会先于灾难

世界基调是平和、繁盛、有烟火气的日常。危机从真实运转的生产和关系中长出，不能用末世、全员阴谋或无差别黑暗替代复杂性。

### 2.4 系统先于一次性脚本

任何需要出现三次以上的内容，都必须先有稳定契约、模板、验证器和预览流程。新角色、新 Boss、新任务和新地区不允许每次从空白代码开始。

### 2.5 可验证的深度先于“做完”

功能完成不等于文件存在。它必须能被玩家触发、与其他系统联动、通过测试、有性能证据、有文档、有足够内容承载，并能在发布构建中复现。

## 3. 1.0 产品边界

1.0 是一个完整的单机章节合集，而非抢先体验占位符：

- 3 个地区：江南水路、龙泉山炉、徽州墨岭。
- 18 个大型子地区，每个地区 6 个；每个地区主线不少于 5 小时。
- 21 章主线、18 条成链支线、120 个以上兴趣点。
- 14 个具备多阶段机制和归位结局的 Boss。
- 24 个核心 NPC；每人至少 3 阶关系弧、2 类系统交互，并在 18 条成链支线中拥有独立或共同主角/关键参与弧。
- 两套互相联动的战斗系统：“护牒兵击”与“工灯定印”。
- 两条完整武器体系：伞器、剑器；各自包含架势、工艺、成长和宗师能力。
- 主线约 15.75 小时；主线加支线约 23.25 小时；全收集与精通目标约 30 小时。

精确目录和机器可验证数量以 [`content/design/v1-content-catalog.json`](../content/design/v1-content-catalog.json) 为准。

### 1.0 明确不做

- 不做无缝超大开放世界；采用高密度地区与可控流式子地区。
- 不做 MMO、强联网经济、PVP 或实时多人协作。
- 不承诺 Web、Windows、Android、iOS 同日首发；1.0 先让桌面浏览器达标，再逐端通过输入、性能和平台审核门。
- 不开放任意 C++/WebAssembly 代码模组；首版仅支持受限的数据与资源扩展。
- 不用 JavaScript 重新实现一套玩法；DOM/Service Worker 只承担网页外壳、可访问性、缓存和平台桥接。
- 不用随机生成代替手工关卡、角色关系和剧情因果。

## 4. 技术总决策

正式客户端采用 C++20 游戏核心，Axmol 2.11.x LTS 作为 2D/2.5D 与跨平台宿主，Emscripten 将 Web 构建编译为 wasm32。桌面浏览器是 1.0 必选平台，WebGL2 为渲染基线；Windows/Android/iOS 通过平台适配复用同一 Gameplay，不建立平行代码线。权威 Gameplay 使用地面平面坐标加独立高度/层语义，Presentation 负责斜向投影、遮挡和景深排序，不能反向改写碰撞与命中。

模拟固定 60 Hz，玩法状态与 Axmol 场景树、JavaScript 和 DOM 分离。Canvas 承载游戏画面，DOM 承载 HUD、菜单和辅助功能；IndexedDB 保存本地进度，Service Worker 与 CDN 负责版本化资源缓存。可选云同步使用“修订快照 + 幂等操作日志”，让访客离线游玩和跨设备接续同时成立。

内容以稳定 ID、JSON Schema Draft 2020-12、带哈希 `.tgdpack` 清单和显式迁移为契约源。Python/Node.js 只用于离线生产与校验，不进入关键帧循环。权威机器基线见 [`../content/design/technical-baseline.json`](../content/design/technical-baseline.json)。

详细决策见 [`01-开发者文档.md`](01-开发者文档.md) 和 [`01-developer/19-ADR索引.md`](01-developer/19-ADR索引.md)。

## 5. 产品层级

```text
游戏
├── 地区 Region（5–10 小时）
│   ├── 大型子地区 Subregion（通常 30–70 分钟；终战型可达 90–100 分钟并分段）
│   │   ├── 场景 Cell / Interior / Encounter Space
│   │   └── 兴趣点 POI / 事件 / NPC 日程
│   ├── 主线章 Chapter
│   ├── 支线链 Quest Chain
│   └── 地区归位状态 Region Resolution
├── 系统 System（战斗、关系、工艺、探索、经济）
└── 内容包 Package（版本、依赖、签名、迁移）
```

地区不是背景皮肤。每个地区必须拥有独立的工艺问题、经营循环、材料与生产网络、探索语法、社会矛盾、Boss 机制、NPC 网络、武器或系统扩展，以及可感知的归位后变化。若移除地名和美术后，两个地区仍使用同一批材料、同一工序、同一经营目标和同一关卡解法，则该地区设计不合格。

## 6. 文档宪法

顶层文档永远只有 00–09 共 10 份：

| 编号 | 唯一职责 |
| --- | --- |
| 00 | 全局纲领、不可变原则与范围 |
| 01 | 开发者入口与 10–19 二级手册索引 |
| 02 | 尚未完成的版本规划、门禁与验收 |
| 03 | 已完成版本与事实记录 |
| 04 | 游戏规则、循环、战斗、成长与经济 |
| 05 | 世界观、叙事、组织、术语与正史边界 |
| 06 | 内容分类、模板与生产流程 |
| 07 | 1.0 地区、Boss、NPC 与内容预算 |
| 08 | UI、UX、输入、反馈与可访问性 |
| 09 | 术语、索引、来源与待决问题 |

10–19 只能位于 `docs/01-developer/`，是 01 的二级菜单。新增信息必须先归类；不能因为“暂时找不到地方”就新增顶层文档。架构决策进入 ADR，包内局部说明放在对应目录 README。

## 7. 决策与变更

- 产品支柱、1.0 边界或主技术路线的变化必须写 ADR，并说明替代方案、迁移、风险和回滚。
- 已发生事实写入 03；未来计划写入 02；二者禁止混写。
- 世界新设定先与 05 校验；游戏机制先与 04 校验；生产方法先与 06 校验。
- 内容目录的数量、ID 和引用必须通过 `npm run validate:design`。
- 任何人都可以提出变更，但没有证据的“感觉更好”不能越过发布门禁。

## 8. 质量红线

- 同一概念不允许多套正式 ID。
- 运行时代码不直接读取未经校验的任意 JSON。
- 表现层不拥有战斗真相，编辑器不反向依赖具体地区内容。
- 保存档不能依赖场景节点路径、数组下标或可变显示名。
- Boss 不得只有血量增长；NPC 不得只有站桩对话；地区不得只有换色地图。
- 自动化通过不能替代人工游玩；人工“感觉能玩”也不能替代自动化与性能证据。
- 不用短期赶工给长期系统制造永久例外。

## 9. 历史边界

旧版 Web/Canvas 项目已在 GitHub 分支 `codex/archive-legacy-web-v1` 归档。它保留早期世界构思、内容 JSON、江南雨巷可玩闭环与验证结果，可供研究，但不再定义新主线的架构、目录或发布目标。

主分支只向前演化。需要借鉴旧内容时，应把设计意图迁入新契约，而不是复制旧运行时代码。

## 10. 玩家承诺与成功判定

《天工渡》面向喜欢 2.5D 斜向全景动作、东方幻想、角色关系和探索推理的玩家。它允许玩家用 20–45 分钟完成一段有明确收束的游玩，也允许连续数小时深入地区；浏览器“即开即玩”降低进入成本，不代表系统、叙事或关卡必须轻量。

1.0 成功不是只把目录中的数量做满，而是同时满足：

- 新玩家能在序章理解移动、兵击、工灯、证据和归位，并愿意继续进入江南。
- 熟练玩家能从两种武器、架势、部件、工印、路线与关系协作中形成多种有效解法。
- 每个地区至少提供五小时不靠等待、强制慢走、刷同组敌人或无意义往返填充的主线。
- 玩家在归位后能从空间、人物和记录看见自己的决定，而不是只收到不同奖励数字。
- 刷新、离线、设备切换、更新和失败重试不会让玩家怀疑存档是否安全。
- 新地区与新角色主要通过模板、内容包和既有系统扩展，长期更新不持续放大返工成本。

## 11. 长期更新模型

发布后的基本内容单元是“地区篇章”，不是无限追加数值等级。一个新地区应带来新的工艺问题、探索语法、社会网络、Boss 归位和至少一个可复用系统扩展；旧武器、旧关系和《天工录》记录要能在新地区产生组合价值。

- 1.x 优先修复、平衡、辅助、关系场景、挑战回访和章节型扩展，不随意破坏存档语义。
- 新武器只能在共同输入、命令、效果和工灯接口上扩展，不能复制整套战斗核心。
- 数值天花板缓慢增长，横向用途和组合优先；不能让新地区装备使旧地区全部失去意义。
- 正式内容包可以独立更新，但新增玩法语义必须升级可执行版本/Content API。
- 每个大版本声明可读/可写存档范围、迁移、回滚和停止支持窗口。
- 未完成地区不以“长期运营”为理由切碎到无法形成一段完整体验。

商业模式、付费点和外部发行合作尚未决定；在专门产品决策完成前，禁止把付费、抽取、体力、广告或联网权益写入 Gameplay。任何商业设计都不得破坏访客可玩、本地存档、完整叙事购买边界和单机可恢复性，且必须单独经过产品、法律、安全与平台评审。

## 12. 决策权与否决边界

| 决策 | 最终负责 | 必须会签 | 可否由单个开发者临时改变 |
| --- | --- | --- | --- |
| 产品支柱、1.0 范围、里程碑 Go/No-Go | 制作人 | 游戏总监、技术、内容、QA | 否 |
| 世界正史、角色核心与结局语义 | 叙事负责人 | 游戏总监、内容、相关设计 | 否 |
| 分层、平台、存档、同步和长期依赖 | 技术负责人 | 模块 Owner、安全、运维 | 否，需 ADR |
| 战斗手感、数值和关卡节奏 | 战斗/关卡负责人 | 游戏总监、动画、QA | 仅可调试实验，合入需评审 |
| 安全、隐私、许可和发布门 | 安全/发布负责人 | 技术、制作人 | 有权阻断发布 |
| 自动化与人工验收是否充分 | QA 负责人 | 功能 Owner、制作人 | 有权要求补证据 |

制作人不能以排期压力单方面覆盖存档、安全或 Blocker；技术负责人也不能以架构纯洁度单方面删减玩家承诺。争议先回到证据与本文件支柱，仍无法决定时保留 No-Go，并把取舍写入 ADR/02。
