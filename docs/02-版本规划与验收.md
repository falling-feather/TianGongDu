## 1. 总体开发规划

### 1.1 长期产品预期

《天工渡》的最终价值不是单独的战斗演示，也不是一套编辑器。它要形成“东方工艺社会 → 探索与关系 → 伞器战斗 → 工灯见因 → 选择归位”的完整动作 RPG。三地区、核心 NPC、Boss、工艺和剧情仍是长期内容目标。

当前先做系统型 Demo，是为了在扩大内容生产前证明三件高风险事实：

1. 战斗循环有足够的操作差异和多人压力。
2. 设计师能用工具创建、修改和验证关卡，不靠程序逐项硬写。
3. 同一内容和 Gameplay 能在 Windows/Web 可靠运行、保存和恢复。

这三个事实没有成立前，不恢复长剧情、正式资产和三地区量产。

### 1.2 系统型 Demo 目标画面

玩家从一个小型战斗场地开始：

- 可见并能辨认玩家、障碍、互动机关、安全点和不同职责敌人。
- 移动到控制台，操作机关打开权威碰撞门。
- 依次面对至少两组不同组合的敌人。
- 使用移动、轻重击、防守、闪避、两种架势和每套两到三个有区别的技能。
- 能死亡、重试、离开并重新进入。
- 关卡、机关、波次、敌人和技能状态恢复正确。
- Windows 与 Web 读取同一包并产生一致 Gameplay 结果。

设计师能在编辑器中修改位置、波次、目标和资源，保存后直接重载上述场地。

## 4. 分阶段任务细化

### 4.1 D1｜首个可见 Host

Owner：PLATFORM；主开发集成；QA 必审。

必须交付：

- Windows Axmol 可见窗口与隔离 Web 页面。
- 从同一 canonical `.tgdsbx` 建立 runtime candidate。
- 统一 Action 输入：移动、互动、local retry；禁止复制 F1 键位特判。
- 最小相机、玩家、门、互动点、安全点和四个 Actor placement 的灰盒显示。
- Stable Asset resolver → GPU/renderer 的显式绑定；缺资源保留上一画面。
- 门关闭阻挡、操作后开放、retry 后关闭。
- Window/Web 记录同一 package checksum 和 Gameplay trace。

不包含：两波真正战斗、Objective terminal、完整死亡恢复、正式 HUD 或最终美术。

### 4.2 D2｜编辑器可生产

Owner：TOOLS；CONTENT/DEV/GAME/QA 必审。

必须交付：

- 六类对象新增、复制、删除和反向引用保护。
- 玩家/敌人受控模板与 Stable ID 建议。
- wave/objective 创建、顺序、触发、完成和 terminal 编辑。
- 二维画布拖拽、方向、范围、AABB、层和诊断定位。
- Stable Asset ID 选择与状态提示。
- 保存 → 检查 → Export → Launch → Reload 的完整按钮流程。
- 用唯一系统 Demo 源做正例，负例只由内存 mutation 产生。

### 4.3 D2｜战斗沙盒

Owner：GAME；DEV/TOOLS/ART/QA 必审。

必须交付：

- 通用 player/enemy profile、阵营、职责、loadout 和技能引用。
- 两种架势，每套至少两个有明显差异的主动技能；冷却、消耗、范围和效果由数据定义。
- 三种普通敌人职责：近战压制、远程/骚扰、侧击/包抄；另有一个精英验证位。
- 两到三组敌人组合；多个敌人可以同时施压但有明确进攻令牌和可读提示。
- wave completed → objective completed → terminal 的权威事件链。
- 不按 `system_demo`、F1 ID、资产名称或 fixture 序号分支。

### 4.4 D3｜聚合状态恢复

Owner：GAME/Runtime；Platform、TOOLS、QA 必审。

聚合候选至少包含：

- package/provider identity。
- player pose/resources/stance/cooldown。
- interaction/mechanism/dynamic collision。
- Objective/Wave 状态。
- Actor/Encounter/Combat 状态。
- active safe point 和 Preview generation。

只有全部 prepare 成功才 commit；任一失败保留旧状态。死亡 retry 恢复 authored safe point 和沙盒初态，旧 generation 命令失效；离开返回和整包 reload 分别建立独立证据。

### 4.5 D4｜表现与验收

- UI：生命、体力/定力、技能/冷却、互动提示、重试和编辑器状态；键鼠/手柄/焦点清楚。
- ART：不同对象和敌人不靠颜色也能辨认；攻击前摇、范围、命中和危险方向可读。
- QA：Native 双工具链、Web Single、Chrome/Edge/Firefox、失败/重试/重载、截图、性能和真人试玩。
- 主开发：代码 Review、跨组冲突、最终证据 manifest 和 Demo 版本封装。

## 5. 系统型 Demo 放行条件

以下全部成立才可称“系统型 Demo 可运行”：

### 5.1 工具

- 非程序人员能创建/修改场地、对象、两波敌人和目标。
- 保存、加载、Export、Launch、Reload 可重复。
- 重复 ID、缺资源、断路、越界和不可达路线有准确诊断。

### 5.2 Gameplay

- 玩家基础动作、两架势和首批技能可用。
- 至少三类普通敌人职责、一个精英验证位和一个机制 Boss 验证位。
- 两波战斗、机关门、Objective 和 terminal 都由权威状态推进。
- 重复互动、旧命令和错误顺序不重复推进。

### 5.3 状态

- 死亡 retry 同时恢复玩家、机关、碰撞、波次、敌人和战斗。
- 离开返回、整包 reload 和失败 reload 不破坏 last-valid。
- Profile/奖励回归仍通过；重复奖励不增加 Operation。

### 5.4 平台与表现

- Windows 与 Web 读取同一 package SHA，核心 Gameplay trace 一致。
- Chrome、Edge、Firefox 通过适用路线。
- 每类对象、敌人职责和攻击提示清楚可辨。
- 没有依赖开发控制台、QA hook 或手工改文件的关键步骤。

### 5.5 证据

- 自动化、真实窗口/浏览器、截图/日志、性能和真人试玩都绑定同一候选 commit。
- 至少一名非实现者从编辑器制作/修改场地并完成试玩。
- 已知限制写入发布说明；未完成项不使用 `Verified`、`Preview-ready` 或 `playable`。

## 6. 必须保留的回归基线

系统 Demo 开发不能破坏现有：

- F1 7 Beat、两路线、四阶段 Boss 和两种结算。
- Profile/IndexedDB 奖励原子提交、Head CAS 和 `rewardDedupKey` 去重。
- Native/Web 固定回放和 checksum。
- Quest UI 的权威事件、选择意图和 stale/close 门。
- 两个训练前沿的恢复证据。

这些项目只作为回归门，不再在 02 复制逐提交实现史。精确历史和旧候选边界见 [`03`](03-发布历史.md)。

## 7. 非目标

Demo 完成前不优先：

- 新手引导、长对话、剧情演出和 60 分钟 F1 内容填充。
- 最终角色/场景美术、完整语音和正式本地化。
- Android/iOS 正式版、完整云服务、账号和商业化。
- 三地区量产、完整 NPC 关系网和正式大型 Workbench。
- 任意脚本、无界任务图、通用模组或动态 NavMesh。

出现上述需求时，先登记为后续计划，不得挤占 D1–D4。

## 10. 计划变更规则

- 新事实先更新对应 10–19 开发手册；完成提交再进入 03。
- 当前任务、Owner、依赖、估算或验收变化必须同步本文件。
- 产品支柱或长期技术路线变化必须新增 ADR。
- 阻断项必须写触发条件、Owner、回退和解除证据。
- 任何“完成”必须由 QA 对不可变候选给出明确结论；主开发负责最终集成，不以聊天口头结论替代文档。
