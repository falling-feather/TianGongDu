### 0.2 精简后的协作模型

当前不维持“合同组、包体组、平台组、内容组、UI 组、QA 组”长期同时在线。专业角色仍然存在，但只有遇到具体任务才建立一个短期 Owner。

| 角色 | 当前状态 | 唯一职责 |
| --- | --- | --- |
| 交流组 | 活跃 | 接收用户方向、解释进度、维护高层决策与新主开发交接；不继续承担产品实现 |
| 新主开发 | 活跃；当前 `DEMO-081` | 唯一集成 Owner；直接实现 Web Host、Review、合并和交付，最多维持两条独立功能线 |
| 单任务实现者 | 按需 | 一人认领一个明确任务和一个分支，完成后交还主开发；不形成常驻委员会 |
| 里程碑 QA | 按需 | 只在不可变候选或版本候选出现后验收，不长期占用开发线 |

已归档的长期 QA 与 Platform 任务不再占用置顶或活跃席位；其对话、提交、分支和证据保留。旧 DEV、GAME、TOOLS、CONTENT、UI、ART 等任务继续保持归档，后续不要求“原组复活”，而是按当前版本选择最合适的一名 Owner 直接认领。

### 0.3 一对一认领与并行规则

1. 每个任务只有一个 Owner、一个 task ID、一个分支和一份验收表。
2. 新主开发最多同时维持两条独立功能分支；主开发自己的整合工作不再另建“协调组”。
3. 分支建议为 `codex/demo/<task-id>-<slug>`；任务完成后由主开发 Review 和合并。
4. 普通功能不建立三组会签。默认只需 Owner 自测、主开发 Review；只有存档、支付/奖励、安全、跨版本迁移等高风险改动才增加专项必审。
5. Schema、API 或内容包只是实现某项玩家/生产功能时的手段，不再独立设常驻“合同包体组”。
6. QA 在版本候选上集中执行，不把每个微提交拖入完整三浏览器和远端 CI。

### 0.4 Git 与历史工作树

根工作区由新主开发独占。2026-07-26 的只读审计确认现存 Sandbox、GAME、TOOLS、CONTENT、ART、F1 UI 和旧 Platform worktree 均无未提交文件；但“工作树干净”不等于“分支可以删除”，因为部分成果通过 cherry-pick 集成，单看 `git branch --merged` 会误判。

在 `Demo 0.8.0` 审计完成前：

- 不删除、重置、覆盖或批量清理旧分支/worktree。

- 对每条旧线按 `已集成 / 仍有独有价值 / 可由历史提交恢复 / 无价值候选` 分类。
- 只有“内容等价已验证 + 无未提交文件 + 无独有证据 + 用户或主开发批准”四项同时成立，才删除工作树；删除分支另行确认。

## 1. 总体产品规划

### 1.1 长期产品预期

《天工渡》不是纯战斗游戏，也不是把传统技艺做成图鉴或一键合成的模拟经营游戏。长期体验由三条同等重要的主线组成：

1. **技艺体验**：观察需求、选材、操作工序、试用、发现问题、维修或返工。
2. **工坊与地区经营**：管理材料、工位、订单、品质、关系、供需和公共维护。
3. **探索与战斗归位**：在地区空间中处理失序，让工艺结果改变路线或战斗，让探索和战斗结果回流生产。

三地区必须形成不同的生产、空间和社会语法：

| 地区 | 工艺与经营 | 探索/战斗 | 地区结果 |
| --- | --- | --- | --- |
| 江南水路 | 纸伞、染色、工坊协作、水路市场与公共维护 | 天气、导流、保护和短兵协作 | 伞器调校、行情、水路和维修互相影响 |
| 龙泉山炉 | 选矿、锻造、工序调校、订单信誉和危险劳动 | 温度、受力、材料和垂直矿炉 | 用途与锋利的取舍改变生产规则 |
| 徽州墨岭 | 制墨/砚田、契约、商路、物流和资源分配 | 证据、规则、同伴调度和低战斗裁定 | 记录权、林水资源和商队组织改变地区 |

本阶段只制作江南代表闭环，但所有通用系统必须允许以后用不同数据表达龙泉与徽州，不能把“江南伞作”写成 Runtime 特例。

### 1.2 当前 Demo 的缩小边界

为了尽快看见整体效果，系统型 Demo 暂定为：

- 一个可反复加载的江南小场景。
- 首轮 20–30 分钟，熟悉后 10–15 分钟；不再要求先做 60 分钟剧情纵切。
- 三名代表 NPC：沈砚、骆青禾、阿棠。
- 一段纸伞维护/调校技艺，包含选材、工序、试用和返工。
- 一个小型工坊循环，包含库存、一个订单、品质/成本取舍和交付结果。
- 两种普通敌人职责、一名精英、两波战斗；先验证两种架势与 4–6 个数据化技能。
- 一次死亡/重试和一次离开再进入，工艺、机关、目标、敌人和战斗状态保持一致。
- Web 是最早可见出口；最终 Demo 候选再要求 Windows 与 Web 同包一致。

长剧情、新手引导演出、完整 Boss、三地区量产、24 名核心 NPC、最终美术、移动端和云服务不进入 `0.8.x` 的关键路径。

## 6. 执行节奏

### 6.1 两条并行线

常态只开两条：

- **可见产品线**：Web Host → 战斗/工艺/经营 → 双端。
- **生产工具线**：CRUD/画布 → 波次/目标 → 工艺/经营面板 → Launch/Reload。

内容、NPC 和美术在对应系统已可见时进入其中一条线，不单独长期占组。新主开发负责每日集成判断和每个小版本的单一候选，不同时推进三个互相等待的“基础设施组”。

### 6.2 验证节奏

1. Owner 先跑受影响单测和一条真实手动路线。
2. 主开发 Review 后形成版本候选。
3. 候选再集中跑 Native/Web/浏览器和回归。
4. `0.8.1` 起每个产品版本必须有截图或短录像；只有日志没有画面不得作为阶段成果。
5. `0.8.4` 起每个版本必须至少有一名非实现者试玩。

## 7. 系统型 Demo 放行条件

`0.8.9` 只有同时满足以下条件才能称为 Demo Candidate：

### 7.1 玩家闭环

- 玩家能从 Web 首页进入，不需要开发者命令或 QA 按钮。
- 首轮 20–30 分钟内完成：认识地区需求 → 工艺/工坊取舍 → 打开路线 → 两波战斗 → 交付结果。
- 三名 NPC 各自承担不同系统功能，不用长对话填充分钟。
- 工艺结果至少改变一个探索或战斗解法，战斗/探索结果至少回流一种材料、订单或地区反馈。

### 7.2 编辑器闭环

- 能新增、复制、删除并摆放六类基础对象。
- 能配置资源、波次、目标、工艺、订单和 terminal。
- 保存、加载、导出、Launch、修改和 Reload 成立。
- 重复 ID、缺资源、断路、不可达、图循环和坏引用有可定位诊断。

### 7.3 战斗与状态

- 两架势、4–6 个技能、两普通职责和一名精英均可辨。
- 死亡、重试、离开返回和 reload 不重复推进、发奖或留下半状态。
- Windows/Web 同包、同规则、同固定输入 trace。

### 7.4 表现与质量

- 灰盒可接受，但 NPC、敌人职责、工位、材料状态、机关和攻击提示不能靠颜色单独区分。
- Chrome、Edge、Firefox 和 Windows 候选通过适用门禁。
- 520×800 与 200% 基本可用；键盘/手柄焦点不丢失。
- 至少 5 名目标玩家完成试玩，记录首个卡点、死亡、返工、重复感和实际分钟。

## 8. 必须保留的回归基线

- F1 7 Beat、两路线、四阶段 Boss、双结算和黄金回放。
- Profile/IndexedDB 奖励原子持久化、重复奖励保护、失败重试和 CAS 冲突。
- `.tgdsbx` compiler/provider/Export 的 last-valid 与失败保持。
- Workbench Open/Reload/Save/Apply 的 lease、revision、CAS 和焦点边界。
- Native MSVC/Clang、Web Single 与适用浏览器门。

如果某条回归只保护已确认废弃且无替代入口的实验代码，先在 `DEMO-080/089` 提交删除提案和影响证明，再删除测试；不得为“让测试变少”先删门。

## 9. 代码、分支与历史简化计划

2026-07-26 对 Git tracked 常见文本文件的只读统计约为 98,961 行：

因此“接近十万行”并不等于十万行运行时游戏代码；测试已经接近产品代码规模。但玩家看不到新 Demo 仍然说明工程投入和可见成果失衡，必须处理。

### 9.2 简化顺序

1. `0.8.0`：只做依赖图、构建目标和分支/worktree 分类，不盲删。
2. `0.8.1`：建立唯一新 Demo 启动目标，把旧 F1 与新 Demo 构建入口隔离。
3. `0.8.2–0.8.8`：禁止为了新功能再复制 Host、validator、Profile 或任务状态。
4. `0.8.9`：根据真实覆盖删除不可达适配层、重复 fixture、过期原型和已被统一实现替代的分支；F1 回归需要的代码继续保留或移入清楚的 legacy target。

优先审查体量最大的文件和重复职责，不以行数作为唯一删除依据。所有删除都要回答：谁在运行、谁在测试、替代入口是什么、怎样回退。

## 10. 非目标、风险与变更

### 10.1 `0.8.x` 非目标

- 三地区同时制作。
- 长剧情、新手引导演出和完整对话树。
- 14 Boss、24 核心 NPC 的批量内容。
- 最终美术、正式移动端、完整云服务和大型商业 Workbench。
- 以自动 Tick、fixture 或命令行日志替代真实画面和试玩。

### 10.2 主要风险

| 风险 | 处理 |
| --- | --- |
| 又回到底层合同优先 | 没有直接服务当前小版本可见结果的合同任务不立项 |
| 工艺退化为菜单 | 必须有观察、操作、试用和返工，且影响世界 |
| 地区成为换皮 | 每个地区按工艺、经营、空间、社会与后果五项验收 |
| 多组讨论拖慢 | 单 Owner、一分支、主开发 Review；QA 只在候选出现后介入 |
| 为瘦身破坏历史 | 先做 patch/覆盖审计，删除需独立可回滚提交 |
| Web 很久看不到 | `0.8.1` 是硬门，3–5 天仍无画面就暂停其他新增 |
| 剧情再次膨胀 | 0.8.x 只保留支撑玩法的最短对白和地区语境 |

### 10.3 计划变更规则

- 当前实现写 01/10–19；未来计划写本文件；完成事实写 03。
- 世界正史、地区和角色基准回到 05/07；内容模板回到 06；机器身份回到 JSON/Schema。
- 产品版本变化必须更新本文件的总览和对应任务卡。
- 新主开发启动后，先把自己的任务标题、分支、当前 Owner 和下一版本写回第 0 节。
- 任何“完成”必须给出玩家或设计师可见产物；测试通过但没有真实入口，只能标为内部底座。
